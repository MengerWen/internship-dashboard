# 计算提速续篇：Response 全链列式化、前置筛选与本地 Spool

## 1. 总结范围与核心结论

本文接续 2026-07-22 的《计算提速全记录：从热点优化到零全量落盘与多窗口复用》，只记录该文档之后新增的性能工作。实际改造主要发生在 7 月 24 日至 7 月 30 日凌晨，属于同一轮 7 月 29 日正式链路收口工作，因此统一归入本篇。

这一轮不是只改了一个慢函数，而是依次处理了四层问题：

1. Response 计算反复扫描、反复构造 Pandas 对象；
2. 不可能通过资格检查的候选仍然先做了昂贵转换；
3. 五日校准把数亿行一次性装进内存；
4. 已经改成磁盘临时文件后，又把临时文件错误地写到了 s3fs 对象存储。

最终可复核的结果如下。

| 流程 | 改造前或中间状态 | 改造后实测 | 应怎样理解 |
|---|---:|---:|---|
| 单日候选生成与定标证据链 Task 14 | 3,695.404 秒，约 61 分 35 秒 | 251.294 秒，约 4 分 11 秒 | 同一轮候选数量为 43,372,870，端到端约快 14.7 倍；主要来自前置 Gate、并行利用、热进度与临时盘路径修复 |
| 后续 Task 14 稳定复跑 | — | 243.30 秒；固定 `Xq=10%`、取消普通价格硬门后为 244.76 秒 | 说明不同候选语义下仍能稳定维持约 4 分钟级候选流水线 |
| 五日 Gate 校准 | 全量物化约 2.08 亿行，接近 100 GiB 后被 guard 以 exit 137 安全终止 | 分桶紧凑归约后，五日总计 4,350.8 秒、峰值 20.44 GiB | 先把“不能完成”改成“可完成”；这一版仍受 4 worker 和 Python 对象循环限制 |
| 固定策略五日连续核定标 | Pandas 全量物化约 2.35 亿行，再次触及 100G guard；第一版磁盘 Spool 又因 s3fs/FUSE 极慢 | 最终 wall 1,301.23 秒、CPU 9,215.18 秒、峰值 24.30 GB，较同语义旧运行 1,437.55 秒快约 9.5% | 流式扫描解决内存问题，本地 `/tmp` Spool 解决对象存储往返问题 |
| 正式冻结单日完整 Scorer Task 16 | 早期基线运行超过 5 小时 38 分仍无正式因子完成 | 两次独立运行分别 684.46 秒和 664.36 秒，输出哈希完全一致 | 最终是约 11 分钟完成一个全市场正式因子日；不能把它与只生成候选的 4 分钟 Task 14 混为一谈 |

需要特别说明三点：

- 7 月 24 日冻结的旧基线是“超过 5 小时 38 分仍未完成”的异常长尾运行；最终 Task 16 的日期、候选政策和正式参数均已变化，因此只能说从“无法完成”推进到“稳定完成”，不能严谨地写成一个直接倍数。
- 7 月 28 日大量热点 A/B 使用了后来被真实报价 Tick 审计判定为无效的旧研究参数。它们不能支持参数或因子研究结论，但同一输入、同一输出下的函数耗时比较仍然是有效的代码性能证据。
- 60 个交易日的正式评价后来完成了 41 日后因 Doris FE 没有 Master、`Node catalog is not ready` 而停止。该轮峰值 49.38 GB、无 OOM、无 swap、无 watchdog；所以本文不虚构“60 日总耗时”，也不把数据库故障算成代码性能退化。

## 2. 概念解释

### 2.1 Response

Response 可以理解为：

> 一张订单发生撤单、重挂、追价等动作之前，市场刚刚发生了什么冲击，这个动作是不是对那次冲击的反应？

旧实现会对大量候选关系一次次回头扫描事件表。候选越多，重复扫描越严重。

技术上，Response 需要在严格的时间、事件距离、排除规则和稳定 tie-break 下，为每条候选边查找最优前序市场事件。它不是普通的最近邻查询，必须保持浮点计算顺序与旧路径逐位一致。

### 2.2 Reducer

一张撤单附近可能出现很多候选新单，但最终通常只需要每个因子的最佳证据。Reducer 就是在大批候选中做：

```text
筛选 → 评分 → 去重 → 稳定排序 → 保留每组最优结果
```

旧实现经常把候选拆成许多小 DataFrame，再用 Python 循环和 Pandas groupby 反复处理；新实现尽量把它们一直保留为数组或列式批次。

### 2.3 “有界状态”

旧路径可能随着候选数量增加，把越来越多 winner、字典、集合和 DataFrame 留在内存中。

有界状态的意思是：

> 无论全市场有多少候选，内存中只保留当前分桶、当前批次和最终真正需要的少量最优值；处理完就释放。

技术上，这一轮主要使用 NumPy/Arrow 数组、紧凑整数索引、分桶归约、在线 local-best 和磁盘 memmap。

### 2.4 Spool

Spool 是“暂时放在磁盘上的中间数据”。它不是最终研究结果，用完应该自动删除。

这一轮曾出现过一个典型错误：虽然不再把 2.35 亿行放进内存，却把 6～12 个临时二进制文件交替追加到 s3fs。每次追加都要经过 FUSE 和对象存储往返，因此内存安全了，速度却非常慢。最终做法是：

```text
大量临时数据 → 服务器本地 /tmp
最终 JSON、报告、SHA-256 → 持久化 s3fs
成功后 → 清空 /tmp
```

### 2.5 三种“单日耗时”为什么不能直接比较？

本轮日志中至少有三类任务：

| 任务 | 做什么 | 是否包含完整正式 Scorer |
|---|---|---|
| Task 14 | 生成候选、漏斗、sufficient 统计和单日验收 | 否 |
| Task 15 | 重算五日候选并做连续参数定标 | 否，重点是校准归约 |
| Task 16 | 使用冻结参数计算完整正式因子 | 是 |

所以“Task 14 约 4 分钟”不能被写成“全部因子 4 分钟”；正式全市场因子单日的最终实测是约 11 分钟。

## 3. 2026-07-24：先重构 Response 的重复工作

### 3.1 针对什么问题？

7 月 24 日冻结的真实性能基线显示：

- 正式单日运行超过 5 小时 38 分仍未完成；
- 16 个计算 worker 已启动，但没有正式因子完成；
- `002528` 只有 2,732 个事件、511 条原始 pair，worker 总耗时 9.356 秒；
- 其中 shared 阶段 7.661 秒、pair score reduction 7.286 秒、Response 7.076 秒；
- Response 占单股 worker 时间约 75.6%，占 pair reduction 约 97.1%；
- 重股票 `001257` 有 280,160 个事件，运行约 4 小时仍没有正式因子完成。

大白话说，慢点不是“某个指数函数算得慢”，而是：

> 每个因子都拿着相似的数据重新找一次、扫一次、转成 Pandas 一次，最后只留下几个最优值。

### 3.2 怎么改的？

先做了一轮结构性重构：

1. 只保留真正有消费者的 L2 时间区间，股票处理结束后立即释放父进程中的大 frame；
2. 每个股票只建立一份紧凑 `PairStockContext/ResponseStockContext`；
3. 按因子的语义依赖生成最小 `ResponseReductionPlan`，不用的变换不构造；
4. 把多个 Response 扫描融合成一次 exact scan；
5. 在最终逐值计算前，用严格上界排除绝不可能胜出的 edge；
6. f38、f41、f51 等下游因子复用完全相同的 Response 查询；
7. 用低内存 block index 代替“为整只股票建立巨大树”；
8. 从正式热路径移除 Pandas candidate object；
9. 复用 aggregation alignment、零命中 scorer 结果和公共输出。

技术提交为：

```text
18a556a  prune unused l2 intervals and release stock frames
44db4b7  build one compact pair response context per stock
71708cc  plan response transforms by semantic dependencies
1b1b62f  fuse response scans and prune impossible edges
8b88cfe  reuse exact response queries in downstream scorers
fec7417  add low-memory exact response block index
fa9afe3  remove pandas objects from response reduction
50bcf2f  reuse aggregation alignment and scorer outputs
```

### 3.3 产生了什么效果？

这一阶段把 Response 从“每个因子各做一遍”改成“每只股票共享一次底层计算”。内存不再按全节点 Top-K 方案增长；原方案估算单股可能需要约 768 MiB 的 int32 或 1.5 GiB 的 int64 状态，block index 的估算规模只有约 1～4.7 MiB。

但这轮没有伪造端到端提速倍数。三只小股票的 legacy/optimized 运行虽然都完成，单股约 11.8～15.4 秒，整体 wall 却主要被每轮约 1.6 GB、1,299 个 calibration handoff 文件的复制占据；而且当时冻结参数缺失会使 174 个正式 scorer 全部 `computed=0`。因此这批 canary 只能证明输入与流程基础一致，不能当作最终 Scorer exactness 或正式 wall 结论。

### 3.4 每次修改后的测试结果

- 主回归：759 passed、8 skipped；
- snapshot：92 passed；
- exactness/runner 聚焦测试：80 passed；
- scope change 回归：87 passed；
- progress JSONL 跨进程写入修复后：100 passed；
- 三只真实股票 legacy 与 optimized 均为 3/3 complete、0 failed；
- 两边直接读取行数一致：order 4,366、trade 1,422、cancel 890；
- 后来发现旧 progress JSONL 有 NUL 空洞，比较器正确 fail closed，没有跳过坏行。

## 4. 2026-07-24：删除校准 Handoff 的纯 I/O 浪费

### 4.1 针对什么问题？

小股票本身十几秒就能完成，但每个验收 run 都会复制：

```text
约 1.68 GB
约 1,300 个文件
约 40～50 分钟
```

其中约 1.45 GB、约 86% 是当前正式日内研究已经不使用的 placebo 数据。s3fs 上还会经历“读源文件算 hash → 复制 → 重新读目标校验 hash”，所以少量计算被大量对象存储元数据与复制操作淹没。

### 4.2 怎么改的？

1. 把 evaluation 从“训练+评分”纠正为 score-only；
2. 只读已有校准源，构建最小 runtime bundle；
3. 不复制 March day buckets、placebo、raw rows 和无消费者工件；
4. exactness canary 使用临时输出，比较和摘要完成后删除；
5. 由 guard 直接记录 terminal cgroup CPU、内存和 I/O，不再叠加重复 sampler。

技术提交为：

```text
653624e  make formal evaluation score only
73f8d2a  prepare response runtime without handoff copies
45f241b  record terminal cgroup resource deltas
68d918f  run response exactness canaries ephemerally
```

### 4.3 产生了什么效果？

从执行路径上彻底删除了每次 40～50 分钟、1.68 GB 的重复复制，也避免在评价期重新生成训练和 placebo 工件。

这项收益是“已删除的确定性 I/O 路径”，不是完整单日 A/B：后续旧参数 run 因正确性和研究口径变化被停止、结果删除，因此没有保留一个可与旧 run 直接对账的完整正式单日 wall。

### 4.4 修改后的测试结果

- score-only 与 fail-closed 路径：56 项通过；
- 最小 runtime bundle：32 项通过；
- 计划筛选口径：30 项通过；
- runtime bundle 明确不包含 day buckets、placebo 和 raw rows。

## 5. 2026-07-27：先筛掉不合格候选，再做昂贵转换

### 5.1 针对什么问题？

旧候选流程先在时间窗口内形成大量“旧订单—新订单”组合，完成 Arrow 编码、overlap、价格/数量变换后，才发现其中许多根本不满足候选资格。

大白话说，相当于：

> 先给所有报名者做完整体检，最后才检查报名表是否合格。

### 5.2 怎么改的？

1. 开盘前三分钟研究把候选时间窗口固定为 3 秒；
2. 数量和价格资格 Gate 提前到 Arrow 编码与昂贵 overlap 变换之前；
3. 普通限价与特殊/可成交订单分成两条通道；
4. Response 只看动作前 1 秒；
5. 取消正式路径中的 placebo artifacts 和 placebo factors；
6. 校准器不读取 label、return、IC 或 placebo；
7. 只在通过 Gate 的真实候选上冻结连续核尺度；
8. progress 高频写入本地热盘，checkpoint 才写持久化存储；
9. `parent_retained_bytes` 改成 O(1) 维护，避免每次心跳重新扫描全部保留对象；
10. 对热 scratch 设置明确容量与清理边界。

核心技术提交为：

```text
0914c49  enforce open3m candidate window defaults
b027287  gate pair candidates before expensive transforms
2b072a7  score gated edges with dual quantity and price lanes
e860f12  restrict market response to one second before action
ce721e1  remove placebo artifacts from formal research path
d74aff4  remove placebo factors from intraday inventory
0cdf182  calibrate candidate gates without labels or placebo
3ae27ac  freeze continuous scales from gated observed pairs
8fd02c7  wire gated open3m study through formal runner
```

### 5.3 产生了什么效果？

三只真实股票 canary 共读取 5,047,584 行，wall 659.869 秒、CPU 84.88 秒、峰值约 2.19 GB，small/median/heavy 三类股票均通过，未触发 OOM 或 watchdog。

完整 Task 14 的关键对照为：

| 指标 | 旧运行 | 修复后运行 |
|---|---:|---:|
| Wall | 3,695.404 秒 | 251.294 秒 |
| 倍数 | 1× | 14.705× |
| CPU | 约 4,905 秒 | 1,963.727 秒 |
| 平均有效核数 | 约 1.327 | 7.814 |
| 峰值内存 | 约 9.43 GiB | 约 13.45 GiB |
| 接受候选 | 43,372,870 | 43,372,870 |

修复后阶段分解为：

```text
compute      116.23 秒
extraction    82.33 秒
merge         28.83 秒
```

随后同一条链在最终 revision 上复跑为 243.30 秒、平均 8.04 核、峰值 13.43 GiB、swap=0。这里内存略升是因为更多 worker 真正在并行工作，不是泄漏。

另外，对 60 个 Q2 交易日 `[09:30,09:33)` 的事件量统计共扫描 1,092,397,719 个事件，业务 wall 142.998 秒、查询合计 96.567 秒、峰值 641,744,896 bytes，所有边界验证通过。这证明“3 秒候选窗”的规模估计可以用低内存方法快速完成。

### 5.4 修改后的测试结果

- 主回归阶段：843 passed、14 skipped；
- snapshot：95 passed；
- 后续 Gate/funnel/资源修复后：848 passed、14 skipped；
- 单日 universe：2,885 = 2,880 available + 5 no-evidence；
- funnel、三个 sufficient sink、no-label、no-placebo 全部守恒；
- swap=0、无 OOM、无 watchdog、无 CPU throttling。

### 5.5 这一提速的边界

3 秒时间窗、数量/价格 Gate 和 1 秒 Response 窗口都属于研究语义的一部分。它们减少了工作量，因此是有效的系统提速，但不是“同样工作量下代码快了 14.7 倍”的纯微优化。

14.7 倍还包含 progress 热写入、报告路径、并行调度和临时盘修复。本文将它记录为端到端流水线提速，不把全部收益归因于某一个函数。

## 6. 2026-07-27：五日 Gate 校准改成内存有界

### 6.1 针对什么问题？

第一次五日 Task 15 已完成前半段计算，但校准器把约 2.08 亿候选行及各 cell 的 Python `dict/set/winner` 全部留在内存：

```text
57.5 分钟时 RSS 约 88.3 GiB
60 分钟后 RSS 约 92.3 GiB
最终接近 100 GiB
guard exit 137
killed_by_guard=true
系统 OOM=false
swap=0
watchdog=false
```

这说明服务器不是“内存不够大”，而是算法把全市场中间状态设计成了随数据量增长。

### 6.2 第一轮怎么改：分桶紧凑归约

新的校准器逐个日级 bucket 读取，按股票完成 36 格 winner、coverage 和 margin 归约后立即释放，只在全局保留：

- 计数器；
- 紧凑数值数组；
- 必需的精确分位样本；
- candidate hash 状态。

如果同一 `(date, code)` 错误地跨文件重复，立即 fail closed，避免为了省内存而错误合并。

技术提交：

```text
52c4367  bound candidate gate calibration memory
```

效果与测试：

- 紧凑路径与旧内存算法在 36 格矩阵、candidate hash、推荐 cell 上逐字段一致；
- 全局 winner 保留数明确为 0；
- 聚焦回归 42 passed、6 skipped；
- 全套 848 passed、14 skipped；
- 五日完整运行后来以峰值 20.44 GiB 完成，不再接近 100 GiB。

### 6.3 第二轮怎么改：有界并行和完成即合并

分桶后单进程内存安全了，但串行扫描仍慢，因此又做了：

1. 最多 4 个 bucket 同时在途；
2. 一个 bucket 完成就立刻合并，不让已完成结果在父进程无限排队；
3. progress 心跳写 stderr，guard 可以看到每个 bucket 的真实进度；
4. 记录单 worker 峰值、全 cgroup 峰值、行数和文件耗时。

技术提交：

```text
1b8699d  parallelize guarded gate calibration
```

测试结果：

- 扩展回归 58 passed、10 skipped；
- 全套 848 passed、14 skipped；
- 正式 Task 14 复跑 243.30 秒，候选与旧 revision 完全一致；
- 正式五日 Task 15 扫描 320 个文件后完成：
  - wall 4,350.8 秒；
  - CPU 23,270 秒；
  - 峰值 RSS 20.44 GiB；
  - swap=0；
  - hot scratch=0；
  - business/acceptance 均 pass。

其中约 15 分钟是五日候选主计算，约 56 分钟是 4-worker 网格校准。相比旧版在单核、近 100 GiB 后失败，这一轮首先解决了可完成性与资源上界。

### 6.4 第三轮怎么改：直接从紧凑桶冻结尺度

冻结器原来仍要求旧的完整 candidate 表和旧 `quantity_scale` 列，导致校准已经紧凑化后，冻结阶段又想回到旧数据结构。

修复后直接从 compact gate buckets 读取门槛裕量，用 NumPy 分块保留正值样本并计算六个尺度。

技术提交：

```text
4a3f471  freeze scales from compact gate buckets
```

测试与真实结果：

- 冻结兼容性回归后全套 850 passed、14 skipped；
- 配置绑定的语义/continuation/freeze 测试 28 项通过；
- 冻结 wall 201.4 秒；
- 峰值 9.79 GiB；
- swap=0；
- candidate hash 与 Task 15 完全一致。

### 6.5 仍然剩下什么瓶颈？

后来 4.004 亿行、36 格旧 Gate 校准的总 wall 为 6,235.80 秒，CPU 29,810.69 秒，平均有效核数只有 4.78。阶段分解发现：

```text
前置五日 panel 约 959 秒，能观察到 16 busy workers
Gate calibration 5,276.88 秒，占 84.6%，固定 4 workers
```

## 7. 2026-07-28：加速精确 Response 查询本身

### 7.1 针对什么问题？

启用最终连续评分后，重股票一个 Response batch 约 40 秒。不能通过降低精度、放宽排除条件或改变浮点顺序来换速度，所以优化必须保持：

- 相同时间截断；
- 相同 `math.exp/sqrt` 顺序；
- 相同候选集合；
- 相同 exclusion；
- 相同 tie-break；
- 结果 bitwise 或逐字段 exact。

### 7.2 怎么改的？

这一轮逐步加入：

1. 固定 `p=1` 的精确时间核快路径；
2. consistency 在同一 edge 内只计算一次；
3. 叶子扫描向量化；
4. node/group/time 上界缓存；
5. 更紧的 block 上界；
6. 事件粒度剪枝；
7. leaf winner、range winner 和批量查询向量化；
8. exclusion/profile 批处理；
9. 批量归约输出；
10. 只把连续多个 winner 都被排除的边送入 scalar fallback；
11. 逐阶段 telemetry，区分 query、profile、winner reduce 和 fallback。

对应技术提交从：

```text
ed35973  accelerate exact response time kernels
85b42bd  vectorize exact response leaf scans
59eb03f  cache exact response node bounds
1995907  tighten exact response block bounds
9e75c59  prune exact response at event granularity
dbfc13d  vectorize exact response leaf winners
71d5834  query exact response winners by range
c4ab27c  vectorize exact response batch queries
c4e717c  batch exact response exclusions and profiles
5d39920  reduce exact response outputs by batch
6e47e6b  isolate exact response fallback edges
```

### 7.3 产生了什么效果？

- 重股票首批由约 40 秒降到约 21～30 秒，后续约 25 秒；
- 进一步 telemetry 显示，9,950 条边上的 exact query 只约 0.198 秒、profile 约 0.057 秒、reduce 约 0.109 秒；
- 这说明精确查询已经不再是最大瓶颈，继续优化树结构的收益很小，热点已经转移到 winner/group reducer 和普通 Scorer。

### 7.4 每轮测试结果

- 第一轮时间核：57 项核心回归；
- 完整回归从 855 passed、14 skipped 逐步增加到 859 passed、14 skipped；
- 100 组随机纳秒区间逐位对比通过；
- 扩展时间边界测试 73 项通过；
- Linux 定向 exactness 测试多轮为 20～32 项通过；
- all-or-nothing fallback 的 76 连续排除 winner 反例通过。

### 7.5 没有采用的尝试

曾尝试事件级树，合成数据中 260 个 impact 最多只需访问 8 个 event leaf，内存也能控制在每股 64 MiB 以下；但真实股票首批从约 33 秒退化到 120 秒以上，原因是 Python 树遍历开销大于剪枝收益。该路线被停止，没有计入成功提速。

### 8.3 链条 Response 与 f52

#### 针对什么问题？

`state_adaptive_run` 对每条 chain edge 都重新执行一次 Response 查询，单股超过 130 秒；queue 还会按链反复扫全表。f52 又在 DataFrame 上逐行写回、逐链筛选。

6. local-best 与订单轴在 scorer 间共享。

技术提交包括：

```text

530d94e  amortize pair and row batch setup
```

#### 效果和测试

- f52 最初约 12.6 秒；后续同口径 profile 从约 1.4 秒进一步降到约 0.6 秒；

### 8.4 Pair Scorer、进度写入和执行类因子

#### 针对什么问题？

六个非 Response transform 仍在逐边 Python 循环；不同 scorer 重复复制 DataFrame、重复做同一数组投影；每个因子完成都可能同步写 progress；execution speed 和 queue dilution 又分别逐候选扫描。

#### 怎么改？

1. pair score 只做一次共享数组投影；
2. Response 与普通 reducer 共用同一批精确得分；
3. 六个 transform 向量化；
4. pair scoring projection 融合；
5. factor progress 和 score alignment 分批摊销；
6. 高频 heartbeat 写入受控、低频 checkpoint 才持久化；
7. execution speed 改成数组计算；
8. queue dilution 按撤单锚点预计算，批次只选择；
9. telemetry projection 保持有界，不复制完整候选。

技术提交：

```text

a00e384  vectorize pair scorer transforms
6c53a8e  amortize factor progress and score alignment
9c89ba5  bound scoring telemetry projections
be845d3  vectorize execution speed scoring

```

### 8.5 按 revision 绑定本地运行时缓存

#### 针对什么问题？

服务器代码 checkout 和 Python 依赖位于 s3fs。16 个 worker 启动时分别从对象存储导入相同源码和依赖，会产生明显冷启动和元数据风暴。

#### 怎么改？

从指定 Git tree 构建只读 `/tmp` runtime cache，只包含：

- 已提交源码；
- NumPy、Pandas、PyArrow 等依赖；
- `READY` 标记；
- revision、tree 和完整文件 SHA。

它不包含任何业务数据、output、scratch 或旧 partial。launcher 和 result 必须验证缓存身份，不能靠未记录的环境变量偷偷加速。

技术提交：

```text
8683ab3  bind guarded runs to runtime cache
```

效果是 16 个 worker 从本地缓存导入，S3FS 代码冷启动瓶颈消失；真实数据仍从正式数据源读取。完整回归 870 passed、14 skipped，registry valid，active placebo 依赖与记录均为 0。

- 股票因子失败即时持久化；
- progress JSONL 跨进程锁；

- no-evidence 股票的空结果 metadata；

- validator 直接流式读取 committed sufficient fragments；
- 成功 hot scratch 空目录也必须清理。

其中 validator 对 86,610,000 级投影行的真实验证耗时 29.64 秒、峰值约 553 MiB，说明“严格验证”本身也可以保持内存有界。

## 14. 本轮曾走过但没有计入成功提速的路线

## 16. 最终状态

- 临时 Spool 不再写 s3fs；
- 成功后本地热盘自动清空；
- 所有重任务均有 100G guard、swap、watchdog 和 revision/hash 证据；
- 60 日正式运行的剩余阻塞是 Doris FE 控制面故障，不是本轮代码速度或内存问题。

这一轮最重要的经验不是“多开几个 worker”，而是：

> 先删除重复计算与重复对象，再让候选尽早收缩；对必须保留的海量数值，用有界列式状态和本地顺序 Spool；最后才扩大并行度。这样得到的速度提升才不会以 OOM、输出不一致或研究语义变化为代价。
