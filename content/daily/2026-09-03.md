# 九参数真实数据定标提速：完整单日从 249.17 秒降到 115.89 秒

## 1. 当前结论

本轮新建了旧因子剩余九组结构参数的真实数据定标快路。任务固定使用代表日 `2026-04-22`、深交所全市场、`09:30:00-09:35:00` 完整窗口和真实 L2 数据，不抽股票、不缩时间窗、不读收益标签，也不使用合成样本。

截至 r29，首个完整且正确的可比版本 r21 从 `249.165709` 秒降到 `115.892094` 秒，减少 `133.273616` 秒，降幅约 `53.49%`，速度约为原来的 `2.15` 倍。以严格逐值对照基线 r25 计算，r29 又减少 `3.583867` 秒；16 个工作进程累计的主要计算时间减少 `117.871563` 秒。

当前结果可以确认两件事：

- r29 的业务结果正确，并与 r25 的有效数据列逐值一致；
- r29 的完整业务 wall time 仍高于 `60.000` 秒，所以单日性能闸门是 `FAIL`。

按本轮停止要求，优化停在 r29，不再启动 r30，也没有创建或启动 `2024-01-02` 至 `2026-06-30` 的全时段定标任务。

## 2. 计算口径

本管线只计算九组结构参数所需的最小充分统计量：

| 参数组 | 主要观测 |
|---|---|
| `f16_priority_scales` | 队列优先级和价格优先级损失 |
| `f31_bottleneck_threshold` | f31 瓶颈原始量 |
| `f40_matching_gates` | f40 episode、可行边和全局匹配门限 |
| `lambda40` | 每个合格 episode 的最佳原始 `W` |
| `lambda42` | 每个合格 BBO 事件的最佳原始 `R` |
| `f85_depth_scale` | 最优档双边总深度 |
| `lambda_RV` | 固定 1 秒网格上的有效 RV 区间量 |
| `z12_depth_scales` | bid/ask Top5 深度尺度 |
| `p03_depletion_scale` | p03 定义内的真实耗竭量 |

股票日内按事件、订单或归约后的 episode 等权；日期内按有样本股票日等权；全期按有样本日期等权。分位数使用右连续精确分位数，支持集先排序并对相同值做 RLE，不使用直方图近似。

定标快路没有构造 63 列 scorer 矩阵、经验 CDF、依赖矩阵或 noisy-OR 参数，也没有进入 `capture_order_scores=True` 的完整训练路径。

## 5. 这些优化具体改了哪些热路径

### 5.1 从完整 scorer 链路拆出九参数专用快路

最先做的是缩小任务本身：同一股票日只读取、规范化和因果回放一次，然后在工作进程内同时产生九组参数的 primitive。父进程只接收已经归约的紧凑支持集和计数，不接收全量候选边或完整 scorer 行。

这一步同时建立了：

- 九组固定 schema 和 fail-closed 规则；
- 三层等权与右连续精确分位数；
- 可续跑的按日任务、revision 校验、guard、进度与结果闸门；
- 每个工作阶段和采集器的单调计时，后续优化只追真正的热点。

### 5.2 把通用热循环改成数组和线性扫描

早期 profile 显示，Python 对象、逐行判断和重复排序占用了大量 CPU。保留的改动包括：

- 稀疏结构匹配不再遍历无关组合；
- p03 耗竭采集改成线性归约，后续再编译为数值微内核；
- episode 候选分数批量向量化；
- 有界小图使用 dense assignment，大图使用稀疏精确匹配；
- 生命周期和事件窗口改用紧凑整数/浮点数组；
- 时间戳、方向、事件类型和索引只编码一次，后续采集器直接复用。

### 5.3 收口 F40 全局匹配

F40 一直是最重的单项。围绕它做了多轮严格精确优化：

- 按独立连通分量拆图，避免把无关 episode 放进同一个求解器；
- 小分量走 dense assignment，大分量走稀疏精确匹配；
- 复用匹配求解器导入和预处理；
- 过滤缺失报价后再建边；
- 候选边使用紧凑列式数组，唯一边跳过重复排序；
- 买卖方向分别构图，减少单个问题规模；
- pair 候选边边生成边归约，不再物化全市场候选表；
- episode 成交片段批量构造，避免对象级循环。

这些改动把候选宽表和数分钟级单股计算压了下来，但 r29 中 F40 matching 的累计 worker time 仍为 `253.477` 秒，是当前最明显的剩余热点。

### 5.4 减少支持集归并和落盘开销

九组采集器会产生大量有序支持值。这里先后做了：

- 工作进程内排序和 RLE，父进程只合并紧凑支持数组；
- 支持数组端到端保留为 NumPy/Arrow buffer，避免列表、DataFrame 和 Python 标量来回转换；
- 多组支持集批量合并，并让互不依赖的归并并行执行；
- 单日结果写成 Arrow 日 pack，避免大量小文件；
- 校验器直接理解 Arrow pack，不再为校验重新展开全部行。

r28 到 r29 又把“绝大多数值都唯一”的 RLE 路径向量化，只对重复值保留逐组 `math.fsum`，确保浮点累加语义不变。200 万个唯一值的微基准从 `2.502` 秒降到 `0.279` 秒，约 `8.97` 倍。正式任务的 support reduction 累计时间从 `42.129` 秒降到 `19.031` 秒。

### 5.5 只构造九参数真正使用的事件状态

后续优化继续压缩一次回放的固定成本：

- F42 只构造自身所需的盘口冲击，不再保留无关字段；
- 预状态事件只投影九参数实际读取的列；
- 生命周期从紧凑事件数组直接建立；
- 结构分组所需的运行时属性和主事件整理分离，避免污染公共事件表；
- 查询结果已经按股票代码组织时，不再做额外的全字段排序。

r29 新增 `build_event_stream_from_tables`，直接从源表构造原始事件流，省掉第一次全量标准化和 vendor side 映射；下游只做一次权威 canonicalization。重票 `002565` 的同列事件构造微基准从 `5.455` 秒降到 `3.471` 秒，公共业务列逐值一致。

重复 canonicalization 的单股全日基准为 `0.898` 秒，复用已标准化数组只需 `0.102` 秒，约相差 `8.77` 倍。这也是 r29 规范化与回放累计时间下降的主要来源。

### 5.6 F42 保持精确语义的区间归约

F42 原来会对同一事件窗口中的多个响应逐个做精确最大值归约。最终实现让区间树先给出最大的两个候选；普通区间直接走快速路径，接近并列时用旧公式复核。r28 已通过与 r25 的完整逐值比较。r29 又直接复用按 source side 排序的 impact 数组，合成微基准比 fallback 快约 `1.20` 倍。

F42 累计 worker time 从 r25 的 `104.547` 秒降到 r29 的 `84.924` 秒。

### 5.7 r29 的其余低风险整理

r29 还保留了几项小但稳定的改动：

- `total_weight` 从 Python 生成器累加改为直接映射浮点数组；
- F42 优先使用已经排好序的 source-side impact 数组，旧接口保留精确 fallback；
- 查询计划显式声明只需按股票代码有序，避免下游误触发更宽排序；
- merge/write 保持紧凑 Arrow 日 pack，避免重新展开成 Python 对象或文本 JSON。
