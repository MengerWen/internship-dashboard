# 计算提速再续篇：精确 Pair 热路收口、10% 数量门修复与本地进度热盘

## 1. 总结范围与核心结论

本文接续 2026-07-22 的《计算提速全记录：从热点优化到零全量落盘与多窗口复用》和 2026-07-29 的《计算提速续篇：Response 全链列式化、前置筛选与本地 Spool》，只记录此后为了新增并批量计算 Open5m 高频量价与微观结构因子所做的新一轮提速与代码 polish。

实际工作从 2026-08-06 开始，延续到 2026-08-09 的全历史启动与断点恢复。它们属于同一个“8 月 6 日新因子实施包”，因此统一归入本篇。

这一轮经历了三个看起来矛盾、但实际上必须按顺序解释的结果：

1. 新因子刚接入时，单只股票约 90～99 秒，明显不可能达到单日 6 分钟；
2. 修复运行阶段、内存和 Pair 热路径后，仍曾得到 **113 分 58 秒**的完整单日结果，看起来比老因子慢约 25 倍；
3. 最终确认 114 分钟主要不是因子运算，而是 16 个 worker 在远程 S3FS/FUSE 上争抢同一个进度文件锁。将高频进度写入迁移到本地 `/tmp` 后，同一套 495 列因子只需 **276.811 秒核心计算 / 300.657 秒完整面板命令**，重新进入 6 分钟以内。

最终可复核的核心结果如下。

| 对比口径 | 修复前或中间状态 | 最终实测 | 应怎样理解 |
|---|---:|---:|---|
| 2026-04-01 核心 `daily_compute` | 6,838.11 秒，约 113 分 58 秒 | **276.811 秒，约 4 分 36.8 秒** | 同一 495 列面板约提速 **24.7 倍**；主要收益来自消除远程进度锁串行等待 |
| 完整面板命令 | Guard 6,865.89 秒 | Guard **299.204 秒**；外层独立计时 **300.657 秒** | 只包含面板因子计算，不含 IC 评价、结果打包或压缩；满足 360 秒目标 |
| 平均有效 CPU | 0.568 核 | **14.381 核** | 16 核容量利用率从 3.55% 升至 **89.88%** |
| worker 非计算差额 | 47,699.16 worker-s | **7.26 worker-s** | 原先几乎全部是远程进度文件锁和同步 I/O 等待 |
| 10% 数量门 | 定义存在，但没有在昂贵宽 Pair 构造前真正过滤 | 约 **4.80 亿** raw pairs 在宽批次前被拒绝 | 既修研究口径，也减少后续价格 lane、Response 和归约输入 |
| 最重票内存诊断 | `000890` 单 worker 约 5.8 GiB，71.17 秒 | 第一轮有界批次后约 1.37 GiB，48.98 秒 | 内存约下降 76%，耗时下降 31.2%；后续继续做列投影与 Response 复用 |
| 老因子同日对照 | Open3m `daily_compute=272.51s` | 新 Open5m `daily_compute=276.81s` | 新增 495 列并未造成 25 倍算法膨胀；最终只比老链路约多 1.6% |

最终面板为：

- 2,886 行股票；
- 490 个正式候选因子；
- 5 个诊断列；
- 合计 495 个因子输出列；
- 失败股票为 0；
- 峰值内存约 21.29 GB；
- OOM、swap 均为 0。

最重要的结论不是“又写了几个更快的循环”，而是：

> 海量 Pair/Response 算法必须继续做有界列式归约，但性能测量也必须覆盖进程外壳、进度锁、临时盘和文件系统。否则代码内部已经足够快，整条任务仍可能因为一个 13 MB 的远程热文件慢 25 倍。

## 3. 先冻结“到底测什么”

本轮最早做的 polish 不是改公式，而是冻结性能合同。原因是“单日耗时”可能指完全不同的任务：

| 口径 | 包含内容 | 本轮是否作为 6 分钟验收 |
|---|---|---|
| 面板核心 `daily_compute` | 每日三表进入后，股票级共享工件、scorer、因子聚合与日面板提交 | 是，作为核心算法口径 |
| 完整 panel 命令 | `run_formal_panel.py` 从启动到成功退出，包括调度初始化与最终提交 | 是，作为用户实际等待口径 |
| Evaluation | 读取面板与标签，计算 IC、Rank IC、ICIR | 否，另行计时 |
| 结果打包 | manifest、结果 JSON、证据归档与压缩 | 否，另行计时 |
| JIT 预热 | 小样本加载 Numba 签名与本地 cache | 最终基准在正式计时前完成，并单独说明 |

固定资源合同为：

```text
日期：2026-04-01
提取进程：2
计算进程：16
计算队列深度：32
解析线程：按冻结配置
worker 内部线程：1
内存 Guard：100G
研究窗口：[09:30, 09:35)
性能验收：完整 panel command ≤ 360 秒
```

每次服务器运行必须使用：

- 已推送且服务器 clean 的业务 revision；
- 全新的 output、scratch 和 run ID；
- 独立 Guard manifest、业务日志与资源采样；
- 明确的成功股票数、失败数、输入行数和输出 schema；
- 无 OOM、无 swap、无 watchdog 卡死；
- 未完成的截断样本不能冒充完整日结果。

这一步不会直接少算一条 Pair，但它阻止了后续三种常见误判：

1. 把训练、评价或打包时间混入面板时间；
2. 把预热后的微基准当作冷启动全市场结果；
3. 把 120 秒内先完成的轻票当作全天平均股票。

## 4. 新因子没有按 495 列重复计算

本轮新因子面板的逻辑规模较大：

| 因子层 | 逻辑数量 | 方向投影后列数 |
|---|---:|---:|
| 老 scorer 的连续 count 投影 | 50 | 250 |
| 联合证据共识 | 4 | 4 |
| 订单级微观结构上下文 | 28 | 140 |
| 窗口级量价与流动性状态 | 12 | 60 |
| 算法目的与机制 | 36 | 36 |
| 正式候选合计 | — | 490 |
| 诊断列 | — | 5 |
| 总输出 | — | **495** |

但实现没有按 495 列重复做 495 次底层工作。正式数据流是：

```text
L2 委托 / 成交 / 撤单
  → 一次标准化与事件回放
  → 一次 lifecycle / prestate
  → 一次 Pair / chain / response 共享工件
  → 一次 scorer 矩阵 S
  → 一次订单上下文矩阵 X 与窗口状态 Z
  → NumPy 广播、分组求和与五种方向投影
  → 495 列结果
```

具体 polish 包括：

- 28 个订单上下文共享同一滚动索引，不为每个订单重新切片扫描；
- 12 个窗口状态只计算一次；
- 同族嵌套证据在订单级取最大值，避免重复计数；
- `total / buy / sell / net / absnet` 从同一累计量生成，不重新调用 scorer；
- 目的因子复用 response action profile，不再复制第二套撤退、补单和冲击公式；
- 输出按 64 列 block 写入，单个 block 失败不要求重建共享工件；
- registry hash 写入输出 metadata，防止不同定义的列被误拼接。

全日 telemetry 表明，新加的 L2～L5 显式后处理合计约 374 worker-s，不到本次内部 worker 时间的 1%。因此后来出现的 114 分钟，不能用“因子列太多”解释。

命名也在本轮统一收口：

- 直接来自老 scorer、只修改 count 口径或增加方向投影的列，保留原 `fXX` 编号并增加后缀；
- 控制/比较 scorer 使用 `cXX`，不占用新因子序号；
- 新共识因子为 `f54～f57`；
- 新订单情境因子为 `f58～f85`；
- 新窗口状态因子为 `f86～f97`；
- 新行为目的因子为 `f98～f133`。

这项命名 polish 不直接提速，但使 registry、Notebook、输出列和依赖审计可以一一对应，避免为了“删慢因子”误删共享底层或漏掉隐藏 Pair 依赖。

## 5. 第一轮根因：正式计算误走训练路径

新因子第一次全市场 canary 中，首批股票约 90～99 秒，其中共享阶段占 80～91 秒。495 列矩阵聚合本身只有约 0.1～0.35 秒。

进一步用同一冻结参数对单票分别运行 `all` 和 `evaluation/score` 后发现：

- 错误路径 worker：约 90 秒；
- 正确 `evaluation/score` 路径：5.85 秒；
- 其中一次性 YAML/Numba 冷启动约 3.3 秒；
- 热态共享计算约 2 秒。

根因是 launcher 没有显式传正式阶段，继承了 CLI 默认 `all`。这会为每只股票额外构建训练期 Pair 校准工件，而本次任务只需要用已冻结参数计算因子。

修复后，正式 server task 强制使用 evaluation 语义，并新增回归断言。该修复提交为 `91156b7`。

这一步说明：

> 新旧代码复用越深，越不能依赖通用 CLI 默认值。训练期需要的“完整证据”在评价期可能完全是冗余工作。

## 6. 第二轮根因：Pair 批次过宽导致 OOM 与对象膨胀

纠正运行阶段后，16 路全市场 canary 在 125 秒时触发 100 GiB cgroup OOM：

```text
已完成股票：69
峰值内存：107,374,182,400 bytes
oom_kill：2
平均有效 CPU：13.09 核
```

重票 `000890` 的单 worker profile 显示：

- 原 Pair reducer 一批最多 200 万边；
- 单 worker 峰值约 5.8 GiB；
- 约 7,000～8,000 万次函数调用；
- 单票 71.17 秒。

第一轮处理分成两部分。

### 6.1 Pair 批次先有界化

代理因子的流式批次先压到 10 万边，防止 16 个 worker 同时持有多个 200 万行宽表。后续又根据 JIT、批间固定开销和并发内存带宽逐轮调优，最终保留的是经全市场验证更合适的较大有界批次，而不是一味缩小。

### 6.2 上下文计算改为向量化

以下逐订单操作改成数组路径：

- marketability；
- 订单前同侧/对手侧深度；
- 滚动 RMS 与 max；
- 事件位置映射；
- 常用方向与队列上下文。

`000890` 的第一轮可比结果为：

| 阶段 | 改造前 | 改造后 |
|---|---:|---:|
| 总 worker | 71.17s | **48.98s** |
| 共享阶段 | 50.83s | **40.90s** |
| scorer | 10.00s | **4.48s** |
| 新因子聚合 | 5.80s | **1.71s** |
| 采样 RSS | 约 5.8 GiB | **约 1.37 GiB** |

所有可比因子逐位一致，最大绝对差为 0。相关提交为 `93f42e8`。

随后曾尝试把 100 万边批次继续压到 25 万。最重票却从 78.52 秒退化到 94.49 秒，说明批间固定开销超过缓存收益，因此这项尝试被回退。

## 7. Pair/Response 热路径的多轮列式化

消除 OOM 后，主要成本仍是数百万至数千万 Pair 的派生、Response 查询与局部最优归约。本轮没有改变因子定义，而是逐层消除重复对象、重复查找和无效宽列。

### 7.1 关闭正式 count-only 不使用的候选行指纹

精确候选行指纹用于训练期取证，但正式 count-only 面板不消费逐 Pair 指纹。关闭该路径后，`000890`：

- 48.98 秒降至 37.18 秒；
- 指纹耗时 4.27 秒降为 0；
- 495 个因子逐位一致。

这里关闭的是不参与因子值的逐行取证，不是取消候选漏斗、运行 hash 或最终审计。

### 7.2 只构造实际读取的 Pair 列

旧路径先构造 37 个物理列，再在代理因子中丢掉近一半。新路径只编码正式 scorer 读取的 19 列：

- Pair batch 从 105.1 MB 降到 34.8 MB，约下降 67%；
- 普通股热缓存从 6.39 秒降到 5.97 秒；
- 后续进一步取消 Arrow 中转，直接把 NumPy 投影数组交给 reducer。

相关提交包括 `974f25c`、`ee9283e`。

### 7.3 Response 查询范围只去重一次

12 条 Response 规则过去会对同一个 `(left, right, side)` 范围重复做 `np.unique` 和边界准备。改造后：

- 每批只压缩一次查询范围；
- 多条规则共享压缩结果；
- 重票 545 万条 edge 实际只对应约 14 万种不同范围；
- `000890` 从 35.86 秒降至 33.04 秒；
- 495 列逐值一致。

相关提交为 `5407e50`。

### 7.4 有序扫描代替重复排序和大临时矩阵

Pair 流本身按撤单锚点有序，但旧 Response 与 group reducer 仍会：

- 在每个计算组重复排序；
- 为最多 64 列边界反复构造二维矩阵；
- `vstack` 多个大数组后才进入 Numba；
- 用 Pandas 物化整批，再只保留每组最多数条 winner。

本轮把有效部分改成：

- 有序批次一次线性扫描；
- 编译态有界 Top-K / local-best；
- 原始列数组直接传入 Numba；
- group 状态按组局部连续布局；
- 相同动作与赢家的连续段只计算一次响应核；
- 乱序或不满足证明条件时回退到原精确路径。

代表性结果包括：

- group 热点约 3.24→2.73 秒；
- 新 Response 快路使 `000890` 的响应主段约 9.60→8.62 秒；
- 极端票 `300274` 在一轮唯一键压缩后约 137.2→102.9 秒；
- 去掉 group 巨型堆叠并局部化状态后，group 约 8.29→5.89 秒；
- 每轮真实 Parquet 均与基准逐列、逐值对比，最大差异为 0。

### 7.5 复用日内成交准备

因子面板和标签消费者过去会各自完整清洗一遍成交表。本轮把日内成交准备抽成共享步骤，避免同一天、同一股票重复做时间转换、排序和过滤。该改动在正式仅 panel 测速中不会虚增收益，但对后续“面板 + 标签”历史任务能减少重复清洗。

### 7.6 事件回放与生命周期微内核

在 Pair 之外还做了以下常数优化：

- 数字事件 prestate replay 编译化；
- 常用事件回放 helper 编译化；
- lifecycle replay 减少状态复制和分发；
- 复用已经证明的窗口边界，不重复检查；
- 裁掉未使用的 L2 接收时间戳列；
- 合并 anchor 查找与 Pair batch。

这些优化单项没有 25 倍收益，但能降低真实 16 路计算中的基础常数，并为后续新因子共享同一套事件地基。

## 8. 严格等价剪枝：哪些保留，哪些回退

最重票 `300274` 曾产生约 6,639 万 raw pairs。在数量门未正确前推时，约 3,625 万条边会进入后续精确路径。Response 最终只需要每个撤单锚点的局部最优，因此尝试过用严格上界提前排除不可能胜出的边。

安全条件是：

```text
只有当前真实下界严格大于候选理论上界时，才允许删除候选；
上界相等时必须保留，避免改变 tie-break。
```

这类实验从数学上保持精确，但端到端未必更快。

| 实验 | 候选变化 | 端到端结果 | 处理 |
|---|---:|---:|---|
| 每锚点 pilot 后自适应剪枝 | 重票查询边约 545 万→303 万 | 38.17s，比 37.18s 慢 2.7% | 关闭生产路径 |
| 4 条 pilot | 约 1,661 万→1,524 万 | 重票约 82.09s，有小幅收益 | 后续被更完整方案重新评估 |
| 16 条 pilot | 约 1,524 万→1,333 万 | pilot 3.97s，总 Response 反而更慢 | 回退 |
| 紧 shock 上界 | 1,524 万→391 万 | 上界扫描 9.72s，总票 82.09→84.66s | 回退 |
| 上界游程压缩 | 数学结果一致 | 1,507 万游程，扫描升至 16.12s | 回退 |
| 二阶段紧上界 + 二次 pilot | 查询段降到 2.65s | 总票 79.14s，仍比保留版慢 0.62s | 整支回退 |

这类失败很重要，因为它说明：

> “少查了多少 Pair”不是充分的性能指标。若为了证明安全而先对全部 Pair 排序、建上界或分配大掩码，证明成本可能高于省下的精确查询。

最终代码只保留在全市场或代表性重票上有净收益、且真实结果逐位一致的机械优化；Numba 微函数单独变快但完整 canary 变慢的提交也被明确 revert。

## 11. 本轮最大提速：把进度热文件移出 S3FS/FUSE

### 11.1 根因

当时的 derived scratch 路径是：

```text
/home/wenjie/hdd-store/tmp/.../derived
```

名字中虽然有 `tmp`，但 `/home/wenjie/hdd-store` 实际挂载类型是 `fuse.s3fs`，属于对象存储 FUSE，而不是服务器本地盘。

16 个 worker 每只股票会多次执行：

```text
打开统一 lock 文件
→ flock(LOCK_EX)
→ 打开 progress JSONL
→ seek 到末尾
→ 写入并关闭
→ 释放全局锁
```

本次共写入 17,648 次、约 13.2 MB。数据量很小，但每次写都要经过远程文件系统，并且全局锁把 16 个进程串行化。最终文件还出现 10 条无法解析的记录，说明这不仅是性能问题，也是不可靠的进度持久化方式。

### 11.2 修复

提交 `40a29bc` 做了四层保护：

1. `progress_hot_root` 不再默认绑定 derived scratch；
2. 正式 Open5m 入口显式创建本地 `/tmp/sirui-open5m-progress-*`；
3. 启动前检查文件系统类型，拒绝 FUSE/S3FS、NFS、CIFS 等远程热路径；
4. Numba cache 同样切换到本地 `/tmp`，避免共享网络盘 cache 锁与偶发 I/O 错误。

持久化对象仍写入 S3FS：

- 最终 Parquet；
- manifest；
- Guard 与资源证据；
- 最终日志和结果 JSON。

只有高频、短生命周期、可恢复的热文件进入本地 `/tmp`。

## 12. 为什么老因子 4～6 分钟，新因子最终也能回到 5 分钟

同日、同一 2,881 只有 L2 数据股票的老 Open3m 正式结果为：

```text
daily_compute = 272.51 秒
raw pairs     ≈ 8.08 亿
accepted      ≈ 6,074 万
平均 CPU       = 14.876 核
```

新 Open5m 最终结果为：

```text
daily_compute = 276.811 秒
raw pairs     = 9.631 亿
accepted      = 7,189 万
平均 CPU       = 14.381 核
```

新路径的原始事件和 Pair 确实更多：

- 窗口从 3 分钟扩大到 5 分钟；
- raw pairs 约增加 19%；
- accepted pairs 约增加 18%；
- 新增订单上下文、窗口状态和目的因子。

但最终耗时只从 272.51 秒增加到 276.81 秒，约增加 1.6%。原因是：

1. 新因子没有重复回放和重复枚举 Pair；
2. 490 个正式列大部分是共享 scorer/context 的向量化投影；
3. 10% 数量门在宽 Pair 构造前拒绝约一半 raw pairs；
4. Pair/Response 的重复范围、宽列、Pandas 物化和大临时数组已被压缩；
5. 最关键的 16 worker 终于真正获得约 14.4 核，而不是在远程锁上睡眠。

因此，先前“114 分钟说明新因子太多”的判断并不成立。正确表述应是：

> 新因子增加了真实算法工作，但增加量仍在共享计算架构可承受范围内；114 分钟是执行层退化，修复后新旧同日核心计算重新处于同一量级。

## 13. 进度、Parser、调度和查询顺序的 polish 与回退

本轮还系统测试了多个容易被直觉误导的工程旋钮。

### 13.1 进度事件合并

保留：

- 股票开始、完成、失败；
- 40 秒心跳；
- 股票最终阶段摘要；
- 日级与 Guard 终态。

取消：

- 每个 Response 小批次都同步落盘；
- 无助于恢复的高频阶段事件。

曾尝试让每个 worker 生命周期内复用文件描述符，普通股票一度从 8～24 秒降到约 1.4～2.0 秒。但该共享文件系统产生 70,653 个 NUL 空洞，破坏日志可靠性，因此完整回退。最终采用“原子追加语义不变 + 热路径本地化 + 降低非必要频率”。

### 13.2 Parser 线程

把三路流式解析各自提升到 4 线程后，名义线程数约 28，与 16 核配额严重超额订阅：

- 120 秒只完成 52 只；
- 原基线为 118 只；
- 单票平均膨胀到约 26 秒。

该参数调整被回退。结论是解析线程必须服从总 CPU 预算，不能只看单流速度。

### 13.3 重票限流与 NUMA 绑核

尝试把 ≥10 万行重票同时运行数限制为 4，其余槽位由轻票填充。120 秒结果为 90 只，低于基线 118 只；重票被推到尾部形成新的长尾，因此回退。

NUMA/绑核实验在相同 120/180 秒窗口分别少完成约 6.4% / 1.9%，也未采用。

### 13.4 Doris 物理排序对齐

尝试让查询顺序匹配 Doris 存储键，再由客户端恢复规范事件顺序。120 秒仅完成 91 只、526 万行，低于 118 只、720 万行基线，因此恢复规范查询顺序。

### 13.5 Numba 微内核

若只看单函数，编译态 local-best、Response lookup 和 trigger exclusion 均可变快；但完整 16 进程 canary 还要承担：

- 每 worker JIT/cache 加载；
- 普通股票小批次调用成本；
- 16 进程同时访问 cache 与内存带宽；
- Windows/Linux、NumPy 版本的末位差异测试。

其中一轮极端票 Response 子阶段从 7.51 降到 5.04 秒，但全市场 120 秒只完成 79 只，低于 118 只。因此相关生产提交被 revert；只保留有明确全市场净收益的编译核。

## 14. 完成者偏差：为什么“120 秒完成 118 只”不能外推

此前 `d0fe989` 的 120 秒截断样本为：

```text
完成 118 只
处理约 719.89 万行
累计约 1,768 worker-s
```

这个数字本身没有算错，但存在完成者偏差：

- 已经开始、尚未完成的重票不计入 118；
- 这些在途股票已经消耗的 CPU 也没有进入已完成 worker-s；
- 调度器前后股票的 Pair 密度不均匀；
- 最后收尾常由少数重票决定，而不是由已完成轻票均值决定。

完整运行进一步确认：

- 当日 2,886 只股票，2,881 只有 L2 数据；
- 输入为 27,304,427 行；
- 重票 `300274` 一度产生约 6,639 万 raw pairs；
- 股票输入行数下降时，Pair 密度也不保证单调下降。

因此，本轮正式进度与性能报告新增：

- expected stock count；
- processed / running / pending / failed；
- 累计输入行覆盖；
- 已完成与在途 worker 时间；
- 日级封口时间；
- Guard CPU、内存和 I/O 终态。

只有完整日 manifest 与 Guard 成功退出，才能作为真实单日耗时。

## 15. 全历史运行前的 O(D²) 预检优化

单日达标后，任务扩展到 2025-01-02～2026-06-30。此时又出现一个与因子无关、但会拖住整个项目的前置问题：报价 tick 审计对每个日期反复扫描此前全部历史，复杂度接近 O(D²)。

359 个交易日会形成数亿次重复日线检查。第一版运行超过 10 分钟仍未完成，而且正式 panel 尚未启动。

提交 `0ee96e3` 与 `f7a79f7` 将其改为：

1. 每个股票日规则元数据只解析一次；
2. 预先建立按股票、日期索引；
3. 每日经验网格只保留最后 20 个真正影响结果的有效交易日；
4. 当日异常检查行单独加入；
5. 新算法与旧穷举 payload、validation hash 逐字段一致；
6. 任一异常仍 fail closed，不因提速而绕过审计。

100 项相关测试全部通过。线性版本能在数分钟内扫描约 70 万个 stock-day，并把后续时间用于真正的 16 worker 因子计算。

这项优化不计入 2026-04-01 的 300.657 秒 panel-only 数字，但对 354 日正式运行是必要的端到端 polish。

## 16. 历史数据正确性 polish 与安全续跑

线性审计加快后，历史数据中的真实异常更快暴露出来。

### 16.1 停牌占位日不再污染价格网格

`000851` 和 `300379` 的近 20 日历史中存在大量静态 OHLC 占位行。成交量、成交额和成交笔数均为 0，不应被当作真实成交价格网格证据。

修复后：

- 无成交占位日不参与经验 tick 网格推断；
- 当日涨跌停字段、元数据覆盖和缺失检查仍保留；
- 不降低 fail-closed 强度。

### 16.2 退市整理期首日豁免必须有官方证据

审计发现若干涨跌停价为 0 的股票日。核对深交所公告后确认它们是退市整理期首日，规则允许首日无涨跌幅限制。

本轮先补入 9 个有公告支持的身份；后续 292 日运行完成后，又发现 `300344 / 2026-03-31` 缺一项。经完整后 62 日诊断确认只有这一项，再提交 `458e855` 补齐。

处理原则是：

- 先收集完整异常清单；
- 逐项核对官方公告、日期和证券代码；
- 把证据写入冻结豁免目录；
- 不能把未知异常改成静默通过。

### 16.3 版本化 guarded resume

原全历史任务在完成前 292 日后，于后段预检因 `300344` 主动停止。它不是 OOM、CPU 或 watchdog 故障：

```text
已完成交易日          292
结果规模              约 29 GB
平均有效 CPU          约 14.85 核
峰值内存              约 95.2 GiB
OOM                    0
```

新增的续跑器 `f2bd015` 具有三道保护：

1. 只允许固定的全历史区间；
2. 必须验证前 292 日完成清单与版本来源；
3. 启动前备份旧失败 Guard，并继续受 100G Guard 保护。

续跑日志明确给出：

```text
processed=0
skipped=292
failed=0
```

因此前 292 日没有重算。后 62 日完整报价预检为 62/62 通过，随后恢复 16 worker 计算。

这类恢复机制不会让单次新计算更快，但能把“一个历史例外导致 292 日重算”的灾难性成本降为只计算剩余日期。

| Response 自适应 pilot / 紧上界 | 查询边大幅减少，但排序、上界扫描和 pilot 成本抵消收益 | 生产路径关闭或完整回退 |
| Pair 批次继续降到 25 万 | 重票 78.52→94.49 秒 | 回到更合适的较大有界批次 |
| 重票并发上限 4 | 120 秒 90 只，低于 118 只基线 | 回退 |
| 三路 Parser 各 4 线程 | 120 秒 52 只，发生 CPU 超额订阅 | 回退 |
| Doris 物理排序键查询 | 120 秒 91 只 / 526 万行，低于基线 | 恢复规范顺序 |
| worker 持久文件描述符 | 速度一度提高，但产生 70,653 个 NUL 空洞 | 回退，改成本地热盘 |
| NUMA 绑核 | 120/180 秒窗口分别少 6.4% / 1.9% | 不采用 |
| 单函数 Numba local-best / Response | 极端票子阶段变快，全市场 120 秒仅 79 只 | 回退相关生产提交 |
| GPU 原型 | 服务器有 RTX A6000，但没有进入正式实现 | 按研究决定停止，不计入成果 |
| 只看 120 秒完成股票数 | 存在明显完成者偏差 | 改用完整日 manifest 与 Guard |

这一节必须保留，因为 Git 历史中存在多次“优化提交 + revert”。如果只列做过的尝试而不写最终状态，会误以为所有代码都叠加在生产路径中，也会夸大实际提速来源。

## 19. 正确性与性能验收

本轮性能优化始终使用以下闸门：

### 19.1 数值与语义

- 真实重票优化前后 Parquet 逐列、逐值比较；
- 最大绝对差为 0 才视为精确通过；
- Pair tie-break、相等上界和事件顺序不变；
- 固定 10% 数量门 raw/basic/segment/quantity/accepted 漏斗可审计；
- 09:35 后事件不得影响 `[09:30, 09:35)` 因子；
- 不使用 label、return 或 target 构造因子；
- 未知方向活动为 0，公共分母保持全订单 count 口径。

- 100G memory Guard；
- 记录父/子 cgroup CPU 与 throttling；
- 记录 OOM、oom_kill、swap、峰值 RSS；
- worker、队列、在途任务和进度文件持续可观察；
- output/scratch 分离；
- Numba 与 progress 热文件必须位于本地临时盘；
- 服务器 checkout 必须 clean 且 revision 已推送；
- 失败 root 不复用，成功历史结果只通过受保护 resume 复用。
