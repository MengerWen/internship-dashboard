# 从搓快照到服务器全市场因子：订单簿重建能力在当前项目中的复用

> **状态口径说明：** 本文虽然按日报顺序放在 `2026-06-26.md`，但内容是站在项目最终状态上，回看 6 月 25 日“重建订单簿 + 搓快照”任务后来怎样迁移到公司服务器、怎样进入 Open5m 因子流水线。本文统一采用完成态口径：服务器全历史计算已经全部完成；执行过程中出现过的中断、续跑和阶段性进度只属于历史过程，不能再被写成当前状态。

## 一、旧项目没有消失，而是从“成品”变成了“地基”

- 6 月 25 日的项目，最终交付物是 100ms 和 3 秒订单簿快照。
- 当前项目，最终交付物则是股票日因子、收益标签、IC/RankIC 评价、Notebook 和后续机器学习数据集。
- 有一条非常清楚的继承关系：

```text
旧项目：逐笔流水 → 重建盘口 → 定时拍照 → 验证盘口正确

当前项目：逐笔流水 → 重建盘口与订单状态
                    → 提取每个动作发生前的市场状态
                    → 识别订单生命周期、重挂、订单链和市场响应
                    → 聚合成股票日因子
                    → 与未来收益做正式评价
```

所以，当前复用的核心是生成快照之前的那套能力：

1. 知道委托、成交、撤单三张表分别表示什么；
2. 能把三张表合成一条因果顺序正确的事件流；
3. 能维护“订单号对应的剩余量”和“每个买卖价位的排队量”；
4. 能在任意事件发生前后得到当时的买一卖一、深度、价差和累计成交状态；
5. 能处理市价单、特殊订单和订单引用缺失等微观结构边界。

换句话说，原项目回答的是：

> **“我能不能把交易所逐笔流水正确还原成盘口？”**

当前项目进一步回答的是：

> **“盘口还原正确以后，逐笔订单在什么市场状态下出现、怎样撤掉、怎样重挂、怎样成交、怎样引发后续市场响应，这些行为能不能形成有预测价值的因子？”**

## 二、当前这一步到底在做什么

### 2.1 当前主任务

本次服务器正式任务是 **Open5m 全历史因子银行**。它使用每天开盘后前 5 分钟，即 `[09:30:00, 09:35:00)` 的 L2 订单流，构造一套覆盖深市普通股的高频行为与微观结构因子。

当前冻结的正式研究区间是：

- 请求范围：`2025-01-02` 至 `2026-06-30`；
- 校准排除日：`2026-03-23` 至 `2026-03-27`；
- 正式接收的交易日：354 日；
- 市场范围：深市普通股，代码以 `0/3` 开头；
- 因子证据窗口：`[09:30, 09:35)`；
- 收益锚点：严格早于 `09:35` 的最后一笔有效成交；
- 收益目标：`[09:44, 09:45)` 的成交 VWAP；
- 输出：490 个正式候选因子 + 5 个诊断列，共 495 列。

上述范围内的 **354 个正式交易日已经全部计算完成**。

这条流水线已经把数百个交易日、数千只股票、数亿级逐笔消息归约成可复用的股票日因子数据。完整的全历史结果现在是后续单因子评价、相关性分析和机器学习研究的统一数据源；下游任务可以直接消费完整的 factor blocks 和 labels，不需要等待这批 Open5m 全历史计算继续补齐。

### 2.2 这一步的直接产物

本次正式任务没有生产全日 100ms 盘口，而是生产并完成了以下几类派生数据：

| 产物 | 大白话解释 | 技术用途 |
|---|---|---|
| `event prestate` | 每次下单、成交、撤单发生前，市场当时长什么样 | 判断订单是否贴近买一卖一、前面排了多少量、对手盘是否薄、价差是否宽 |
| `lifecycle` | 每张订单从提交到成交、撤单或窗口结束的完整档案 | 计算撤单率、寿命、部分成交、主动性和终态 |
| Pair | 一张旧订单和一张可能的替代订单之间的候选关系 | 识别撤单重挂、改价、拆单、并单等行为 |
| Chain | 多张相互关联订单组成的连续执行链 | 识别算法拆单、连续执行、重新定价和流动性切换 |
| Response | 订单行为前后的盘口变化 | 判断行为是否伴随队列稀释、深度消耗、价差变化、波动跳升等影响 |
| Factor block | 把同一股票同一天的大量订单行为压成若干数值列 | 用于股票横截面比较、IC/RankIC 和机器学习 |
| Intraday label | 09:35 后实现的未来收益 | 检验开盘前 5 分钟订单行为是否具有预测信息 |

这些产物都属于不可逆或高度归约后的研究数据，不能从中恢复完整的逐笔原始流水，因此允许写入服务器输出目录。完整 `order/trade/cancel` 原始行和标准化后的完整事件流只允许在内存中短暂停留，不允许重新缓存成另一套 Parquet。

## 三、这一步的目的是什么

### 3.1 研究目的：从“盘口正确”走向“行为是否有用”

搓快照解决的是数据工程和市场微观结构的正确性问题。它证明只要按正确顺序回放委托、成交和撤单，就能够还原真实盘口。

但是这只是后续研究的基础。后续真正核心的研究问题是：

- 高频撤单多的股票，后面收益是否不同？
- 一张订单撤掉以后，很快在相邻价位重挂，是普通人工操作还是算法执行痕迹？
- 连续小单、改价链、扫多档成交、补单和撤退，是否反映主动交易压力？
- 同样一类订单行为，发生在宽价差、薄对手盘或拥挤队列中，含义是否不同？
- 买方痕迹和卖方痕迹抵消以后，总量因子是否掩盖了方向信息？

当前项目的目的就是把这些问题变成可以复现、可以批量计算、可以做统计检验的数值因子。

### 3.2 工程目的：一次读取，把昂贵底层工作全部共享掉

当前 495 列并不是把同一天的 L2 数据读取 495 次，也不是为每个因子重建 495 次订单簿。正式设计是：

```text
L2 委托 / 成交 / 撤单
  → 一次标准化与事件回放
  → 一次 lifecycle / prestate
  → 一次 Pair / chain / response 共享工件
  → 一次 scorer 矩阵 S
  → 一次订单上下文矩阵 X 与窗口状态 Z
  → NumPy 广播、分组求和和方向投影
  → 495 列结果
```

这样做的原因很现实：真正昂贵的是读取数亿条逐笔消息、维护订单状态、枚举候选关系和寻找局部响应，不是最后多写几十列或几百列。如果每个因子重复这些底层工作，任务会从几分钟膨胀到无法运行。

### 3.3 生产目的：形成后续研究的统一数据底座

已经完成的 Open5m 全历史结果可以同时服务于：

1. 单因子 IC、RankIC、分组收益和稳定性评价；
2. 逐因子 Notebook；
3. total/buy/sell/net/absnet 等方向口径比较；
4. 因子相关性、PCA 和冗余诊断；
5. 后续 127 个 total-only alpha 因子的机器学习研究。

因此，这项任务形成了后续研究统一读取的 source。也正因为它要被反复复用，日期、股票池、窗口、参数、列顺序、哈希和失败状态都必须冻结；“程序跑完”只是计算结束，只有产物身份和边界也保持一致，结果才具备长期复用价值。

## 四、当前这一步具体是怎么做的

以下将按照正式服务器程序真正执行的先后顺序，把技术原理、代码实现和直观含义拆开说明。当前全历史任务的实际调用链可以概括为：

```text
正式 shell 启动器
  -> 资源保护器 run_guarded.py
  -> run_formal_panel.py
  -> run_formal_windows：为每个交易日建立唯一 QueryPlan
  -> Doris L2 三表流式读取与按股票分流
  -> 三表事件标准化、时间窗口隔离
  -> 订单簿 prestate + 生命周期 + Pair/Chain/Response 共享工件
  -> 495 列股票日因子 + 日内收益标签
  -> 日级原子落盘、完整性 manifest
  -> 全历史 IC/RankIC 评价和最终证据包
```

这条链已经在 `2025-01-02` 至 `2026-06-30` 的 354 个正式接收交易日上全部执行完成。下面出现的“调度、失败保护、resume”都是对已经使用过的实现机制进行说明，不代表任务还没有算完。

### 4.1 第一步：冻结研究口径，再用 L1 确定日期和股票池

#### 技术原理

L2 只告诉程序“市场里发生了哪些逐笔动作”，并不能单独回答“某天是否为交易日”“某只证券当天是否已经上市”“它是不是深市普通 A 股”。如果直接根据 L2 当天有没有记录来反推股票池，会产生选择偏差：没有 L2 行既可能是停牌或无成交，也可能是抽取失败，不能把这些情况混成一种。

因此，正式程序先用 L1 建立一个 **point-in-time（PIT，按当时状态）股票池**，再拿这个股票池去要求 L2。这里的因果方向是“L1 定义当天应该有哪些股票，L2 回答这些股票当天实际读到了什么”，不能倒过来用 L2 是否有数据决定研究对象。

#### 实际怎样实现

1. 上游已经把公司 Doris `l1` 中的交易日历、证券主表和逐日 ST 状态整理成受 manifest 管理的参考 Parquet。正式计算阶段的 `formal_reference.py` **只读取 manifest 选中的本地参考文件**，不会临时打开 Doris、RQData 或其他网络连接。
2. 每个参考分片都要通过文件 SHA256、`provider=DorisL1` 和 `schema_version=l1-v1` 校验。也就是说，正式程序使用的是“由公司 L1 生成并已经验收的版本化快照”，而不是运行到一半又去查询一份可能变化的参考数据。
3. `load_formal_dates` 从已验收的 `trading_calendar` 中取正式日期；日期必须是标准 `YYYY-MM-DD`，不能重复，也不能偷偷用 L2 可用性补日期。
4. `load_formal_universe` 逐日展开证券主表，只保留：

   - `exchange == XSHE`；
   - `security_type == CS`；
   - 股票代码符合 `[03]\d{5}`，即本项目冻结的深市普通股范围；
   - `listed_date <= 当天`；
   - 退市日为空，或 `de_listed_date >= 当天`。

5. 程序同时计算上市天数和 `is_new_listing_60d`，并把当天 `is_st` 合并进来。这里 ST 是 PIT 注释，不是被悄悄删掉的样本；缺失的 ST 状态保持“未知”，不会擅自当成“非 ST”。
6. 每个交易日都会生成股票池 identity。后续日级结果的 fingerprint 会绑定日期、完整代码集合、L1 universe identity、窗口、正式列、代码版本、冻结参数和查询截止时间。任何一个身份发生变化，旧结果都不能被冒充成当前结果。
7. 正式 shell 启动器还冻结了研究区间、排除的 5 个校准日、研究配置、因子注册表、冻结参数 bundle 及其 SHA256。任务不是边算边改规则，而是先把“研究谁、研究哪天、按什么定义研究”全部锁住再执行。

#### 大白话解释

可以把 L1 理解成“学校花名册”，L2 理解成“教室监控录像”。先由花名册确定某天哪些学生应该在研究范围里，再去录像里找这些人；不能因为录像里暂时没看到某个人，就直接把他从花名册删掉。

原搓快照项目主要拿几只指定股票和几天本地文件做正确性验证；当前项目则先固定了 354 天逐日变化的全深市股票池。原项目关心“给我这份数据，我能不能还原对”，当前项目还必须先证明“每天到底应该算谁”。

### 4.2 第二步：为每个交易日生成唯一的 Doris L2 查询计划

#### 技术原理

当前任务同时需要两类时间数据：

- 因子需要 09:35 以前的委托、成交和撤单，其中 09:30 前的事件要用来恢复开盘时订单簿；
- 标签还需要 `[09:44,09:45)` 的成交，但不需要这 9 分钟内的委托和撤单。

最节省且最严谨的办法，不是读取全天三张表，也不是为每只股票单独查一次，而是把所有消费者的需要先合并成“每张表最小必要时间区间”，然后一个交易日建立一个 `QueryPlan`。

#### 实际怎样实现

`FormalEvaluationSpecs.consumer_required_time_intervals()` 根据冻结窗口自动得到以下查询区间：

| L2 表 | 正式读取列 | 时间区间 |
|---|---|---|
| `` `order` `` | `seq, channel_no, code, qty, price, data_time, side, order_id, ord_type` | 当日开始至 `09:35:00`，右端不含 |
| `cancel` | `seq, channel_no, code, qty, data_time, side, order_id` | 当日开始至 `09:35:00`，右端不含 |
| `trade` | `seq, channel_no, code, qty, price, data_time, side, bid_id, ask_id` | 当日开始至 `09:35:00`，再加 `[09:44:00,09:45:00)` |

这里“当日开始至 09:35”在代码里写成 `start=None, end=09:35:00`，目的是保留集合竞价和开盘前状态恢复所需的所有早期消息。`09:35–09:44` 的成交不属于因子或标签的必要输入，所以不会从数据库搬回来。

每个正式日期只建立一个 `QueryPlan`，其中包含当天完整股票代码集合、三张表、逐表字段白名单和逐表时间区间。查询网关 `snapshot/io.py` 接受的是结构化 `DorisQuerySpec`，而不是任意 SQL 字符串，并强制执行：

1. 只能查允许的数据库、表名和列名，禁止 `SELECT *`；
2. SQL 中必须恰好有一个 `date = 'YYYY-MM-DD'`，禁止日期范围扫表；
3. 股票代码必须是经过验证的 6 位代码，子集用显式 `code =` 或 `code IN (...)`；
4. 时间条件只能由经过校验、同日、已排序且互不重叠的半开区间生成；
5. 禁止 `JOIN`、`UNION`、SQL 注释等扩大查询语义的写法；
6. `` `order` `` 作为保留字必须加反引号；
7. 结果必须 `ORDER BY code, channel_no, seq`，从数据库端就形成可流式切股的顺序。

因此，一个需要计算的交易日正常只打开三条生产查询：order 一条、trade 一条、cancel 一条。trade 的两段时间条件仍属于同一条结构化查询，并不会为了标签再把全天 trade 查一遍。

#### 大白话解释

这相当于先给仓库一张精确拣货单：委托和撤单只拿 09:35 前的箱子；成交除了 09:35 前，再拿 09:44–09:45 那一分钟。仓库按股票代码和事件顺序把货排好，一天只发三车，而不是每只股票派三辆车，也不是把全天所有货先运回来再扔掉。

原项目的数据范围已经由硬盘上的 Parquet 文件决定；当前项目则把“读什么”本身也做成了可审计契约。原项目的 I/O 是文件读取问题，当前项目的 I/O 同时还是数据库负载、时间泄漏和可复现性问题。

### 4.3 第三步：流式解析三张表，并在内存中按股票汇合

#### 技术原理

全市场某一天的逐笔数据很大。如果先把三张表完整读成三个 Pandas DataFrame，再按股票切分，会同时占住整天数据和大量临时对象；如果按股票逐只发 SQL，又会给数据库制造成千上万次小查询。

当前实现采用“数据库按股票排序输出、Python 边读边切、计算端边收边算”的流式流水线。它只要求内存中保留有限数量的股票切片和待计算任务，而不是保留完整的一天。

#### 实际怎样实现

1. `iter_table_by_code()` 启动 MySQL 客户端子进程，把生成的 SQL 从 stdin 送入客户端，从 stdout 读取 Doris 返回的 TSV 流，同时持续排空 stderr，避免子进程因为错误输出管道塞满而假死。
2. PyArrow 使用显式字段类型、默认 32 MiB 的 parser block 解析 TSV；数据库空值 `\N` 被按空值处理，不靠 Pandas 猜类型。
3. 因为 SQL 已按 `code, channel_no, seq` 排序，解析器发现 `code` 发生变化时，就把上一只股票的连续批次立刻 yield 给下游；若代码顺序回退则直接报错，而不是继续产生次序不可信的数据。
4. order、trade、cancel 三个生产线程并行读取。`iter_raw_day_by_code()` 为每张表维护 watermark：只有当三张表都已经给出某个代码，或已经明确越过该代码时，才把这只股票交给计算端。
5. 如果一只股票在某张表里确实没有记录，watermark 能证明这是“该表缺腿”，系统会给它一个明确的空 DataFrame；不会因为线程暂时慢就误判为空，也不会凭感觉补数据。
6. 每只股票的 `RawDaySlice` 把三张表的所有权移交给计算任务。任务完成后立即释放父进程对原始 frame 的引用，并核对 retained bytes 必须回到 0，避免循环几千只股票后内存只增不减。
7. 调度器把待计算股票放入按 `input_rows` 排序的 heap，优先处理数据量最大的股票，降低“大票最后堆在队尾”造成的长尾。计算任务通过有界 `ProcessPoolExecutor` 提交，待执行任务数不能超过 queue depth。
8. 正式资源参数为：2 个日级提取 worker、16 个股票级计算 worker、32 个计算队列深度、每条 Doris 流 4 个解析线程、最多同时物化 2 个交易日、每个计算进程内部线程数固定为 1。调度器还要求单日内存估计不超过内存额度的 80%。
9. 查询层记录原始字节数、解析行数、保留/丢弃行数、读取时间和 RSS；调度层记录队列峰值、父进程保留字节、在途 payload 和完成后释放数量。原始 L2 行始终只在内存中流动，查询网关根本不提供原始数据落盘接口。

#### 大白话解释

可以把三张表看成三条同时运行的传送带。每条传送带上的货都按股票代码排好。系统等到能确定“000001 的三类货已经到齐，或者某一类确实没有”以后，就把 000001 这一包交给工人计算；算完立刻腾空箱子，再接 000002。

这既不是“把整个仓库搬进办公室”，也不是“为每件货单独叫快递”。与原来从硬盘筛 Parquet 相比，订单簿算法拿到的股票级三表输入仍然相似，但前面的数据供给方式已经从本地随机读取变成数据库流式生产。

### 4.4 第四步：把 order、trade、cancel 规范成同一条因果事件流

#### 技术原理

订单簿是状态机。状态机能不能重建正确，不只取决于事件内容，还取决于事件发生顺序。委托先进入、成交再扣减、撤单最后退出，与把三类事件分别处理后再拼结果，不是同一件事。

因此，三张异构表必须先转成统一事件契约，再按交易所序号做稳定排序。后面的订单簿、生命周期、配对、订单链和响应模块都只能消费这一份标准事件轴。

#### 实际怎样实现

`snapshot/events.py::build_event_stream()` 先把三张表映射为共同字段：

- `evtype/etype`：`order / trade / cancel`；
- `seq, channel_no, code, ts, qty`；
- `price_i/price_tick`：整数价格；
- `side, order_id, ord_type`；
- `bid_id, ask_id`。

三类事件的不同点被显式保留：

- 委托用 `order_id` 表示新订单，有限价、市场价等订单类型；
- 成交同时带 `bid_id` 和 `ask_id`，因为一笔成交要扣减买卖双方两张订单；
- 撤单通常没有可靠的撤单价格，统一把事件价格设为 0，再通过 `order_id` 回到账本中定位原订单，绝不拿 0 当真实报价。

时间和价格还要经过两层标准化：

1. Doris DATETIME 的 naive 时间按上海交易所本地墙钟理解；如果输入本身带时区，则先转换到 `Asia/Shanghai`，不会对 naive 时间盲目再加 8 小时。
2. 原始元价格乘以 `10000` 并四舍五入成整数 tick 表示，例如 `9.40 -> 94000`。价格档位、盘口字典和相等比较都用整数，避免 `9.4` 在二进制浮点里产生细小误差。

统一事件按 `(channel_no, seq)` 使用稳定 mergesort 排序，并生成不可变的 `event_pos`。稳定排序意味着键相同时保持原输入次序；`event_pos` 则让后续 context、evidence、Pair 和 Response 都引用同一条事件坐标轴，不再各自重新排序。

成交方向也不直接相信供应商 `side`。vendor side 只保留作诊断；正式主动买卖方向要等生命周期账本同时看到买卖订单、提交先后、相邻关系、订单类型和事前对手 BBO 后再保守判断，证据不够就记为未知方向 0。

#### 大白话解释

三张表原本像三本分开的流水账：一本记“新挂单”，一本记“成交”，一本记“撤单”。程序先把三本账逐行撕下来，统一写上时间、频道和序号，再按真正发生顺序排成一条录像带。只有录像带顺序正确，才能知道某次成交扣的是哪张仍然活着的订单。

这一部分就是原搓快照项目最核心、最直接的复用：三表事件契约、整数价格和因果排序没有被推翻。变化只发生在上游数据来自服务器 Doris，下游也不再只为 100ms 快照服务。

### 4.5 第五步：把同一事件轴严格分成 context、evidence 和 future

#### 技术原理

09:30 时的盘口不是凭空出现的。要知道 09:30:00 前后某张新订单面对多少排队量，必须先回放 09:30 前的集合竞价和早期消息；但这些早期消息不能被当成“开盘 5 分钟出现的算法证据”。同样，09:35 之后的成交虽然可以用来做收益标签，却绝不能回流到因子。

所以当前系统不是简单地截一段 DataFrame，而是在统一事件坐标轴上建立三个互斥、穷尽的视图。

#### 实际怎样实现

| 视图 | 严格时间定义 | 可以做什么 | 不可以做什么 |
|---|---|---|---|
| `context_events` | `ts < 09:30:00` | 恢复 09:30 开始时的在簿订单、价位深度和 FIFO 队列 | 不生成 Open5m scorer 目标，不计入前 5 分钟订单分母 |
| `evidence_events` | `09:30:00 <= ts < 09:35:00` | 生成事件前盘口、生命周期、Pair/Chain/Response 和因子 | 不能读取 09:35 以后的结果 |
| `future_forbidden` | `ts >= 09:35:00` | 因子侧只保留隔离边界；标签消费者按独立规则取成交 | 不能进入 factor replay positions |

`canonicalize_event_block()` 只标准化一次事件，然后生成 context positions、evidence positions、future positions 和 `replay_positions=context+evidence`。三组位置必须互不相交且合计覆盖全部事件；时间越界或 context 序号跑到 evidence 后面都会报错。

虽然同一个 trade 查询还带回 `[09:44,09:45)` 的标签成交，但 FormalPanelConsumer 传给订单簿和因子构造器的只有 `replay_positions`。标签由另一个消费者读取同一股票切片，并且在调度依赖上明确要求对应 factor consumer 先成功。于是“共享一次数据库读取”与“因子绝不看未来”可以同时成立。

#### 大白话解释

可以把数据分成三间房：

- 第一间房负责把舞台布置成 09:30 开盘时真实的样子；
- 第二间房才是因子观察的正式表演；
- 第三间房放的是之后公布的结果。

第二间房的人可以继承第一间房布置好的舞台，但绝对拿不到第三间房的答案。原快照项目主要按交易时段生成整天时间网格；当前项目则把 09:35 做成不可跨越的研究信息边界。

### 4.6 第六步：逐事件回放订单簿，并记录 action-before prestate

#### 技术原理

旧项目在固定 100ms 时点输出“消费完这个时点以前所有消息后的盘口”。当前因子研究要回答的是另一类问题：**某张订单采取动作的那一刻，它事前面对的市场是什么样？**

如果一条新买单先进入订单簿，再读取盘口，这张订单自己的数量就会被算进 `qty_ahead` 和深度，产生自我污染。因此必须遵守 action-before 因果顺序：先拍当前事件执行前状态，再应用当前事件。

#### 实际怎样实现

订单簿仍由复用的 `snapshot/orderbook.py::OrderBook` 维护：

- `orders` 保存 `order_id -> side, price, remaining`；
- 买卖两侧价位字典保存每个价格的总剩余量；
- 限价单 `L` 在合法价格休息；市场单 `M` 不会以价格 0 挂进盘口；特殊 `U` 单只在规则允许且能观察到本方 BBO 时映射价格；
- trade 同时扣减 `bid_id` 与 `ask_id`；cancel 根据 `order_id` 扣减原订单；
- 非严格恢复模式遇到未知引用时可以继续维护可恢复的 BBO，但异常不会被正式生命周期吞掉。

`build_event_prestate()` 对 context 和 evidence 顺序回放。每条 evidence 事件的执行顺序严格是：

1. 删除最近成交队列中早于 1 秒 lookback 的旧成交；
2. 从当前 OrderBook 和深度索引读取事前盘口；
3. 把事件展开成 action leg：委托一条、可定位的撤单一条、成交买方和卖方各一条；
4. 为每个 action leg 写一行 prestate；
5. 把同一事件交给正式 lifecycle replay；
6. 最后才把当前 order/trade/cancel 应用到 OrderBook、深度树和 FIFO 树。

context 事件只执行第 6 类状态恢复，不输出 prestate 行，也不会给 evidence 窗口的“最近 1 秒成交”偷偷预热。也就是说，09:29:59.9 的成交可以影响 09:30 时订单是否还活着，但不会被算成“开盘后最近成交压力”。

每个 action 的主要事前变量包括：

- BBO：买一、卖一及其队列量；
- 买卖 top-N 价格数组和数量数组、top-N 深度与全深度；
- 当前价差 `spread = ask1 - bid1`；
- 盘口不平衡：

```text
book_imbalance = (bid_topN_depth - ask_topN_depth)
                 / (bid_topN_depth + ask_topN_depth)
```

- microprice：

```text
microprice = (ask1 * bid1_qty + bid1 * ask1_qty)
             / (bid1_qty + ask1_qty)
```

- 当前订单价格档已有量、同侧/对手侧深度；
- `qty_ahead_pre = 所有更优价格的同侧量 + 同价格下更早进入的订单量`；
- 最近一笔可判定成交方向、最近 1 秒成交笔数和成交量；
- BBO、深度、FIFO 和方向证据是否完整的 coverage/eligibility 标志。

为了让 `qty_ahead` 不必每次遍历整本订单簿，当前实现把可见价格坐标固定下来：价位总深度用 `_DepthIndex`，同价位时间优先队列用 `_PriceTimeFifo`，内部以 Fenwick tree 做前缀和。这样查询“更优价位有多少量”和“同价位我前面有多少量”可以在对数复杂度内完成。

#### 大白话解释

旧 100ms 快照像“每隔 0.1 秒给整个路口拍一张照片”；现在的 prestate 像“每辆车做变道动作前，立刻拍下它当时看到的路况”。后者能回答“它是不是因为前方拥堵才变道”，而前者往往只看到变道完成后的画面。

这里不是把旧订单簿丢掉重写，而是继续用旧状态机维护真实盘口，再增加事件级快门、深度索引和 FIFO 排队量，服务更细的行为因子。

### 4.7 第七步：用独立整数账本重建正式订单生命周期

#### 技术原理

OrderBook 的首要职责是尽量恢复盘口。为了让回放在脏数据上继续，它在非严格模式下可以记录未知引用、对超减做恢复性处理。正式研究的生命周期不能照搬这种容错结果，否则一张“提交 100、却被扣了 120”的异常订单可能被悄悄修成 0，看起来仍然合法。

因此，当前程序另外维护一套不裁剪的整数 ledger，原样累计每张订单收到的成交和撤单，并用数量守恒判断这张订单是否可观察。

#### 实际怎样实现

context 中出现的订单会进入 ledger，以便 09:30 后的成交和撤单能够找到引用；但只有 evidence 窗口内的新委托会被物化为正式目标行。每个目标保存提交身份、事前 BBO、参考价格、方向、类型和 eligibility，并累计所有子事件。

核心数量方程是：

```text
submit_qty = traded_qty + cancelled_qty + live_qty_at_09:35
```

程序不会把负剩余量裁成 0，而是保留并记录具体异常，例如：

- `duplicate_terminal`：订单已经终止后又收到终止事件；
- `nonpositive_child_qty`：成交或撤单数量非正；
- `over_reduction`：子事件扣减超过剩余量；
- `negative_remaining`：账面剩余量变为负数；
- missing bid/ask/cancel reference、跨方向引用等 reference anomaly。

窗口结束时，订单被归为：

- `filled`：完整成交；
- `partial_cancelled`：先部分成交、后撤销剩余部分；
- `unfilled_cancelled`：未成交即撤销；
- `live_at_0935`：09:35 时仍存活，即右删失，不能假装后来一定成交或撤单。

只有同时满足以下条件时，`observable_for_lifecycle=True`：

1. 数量守恒成立且剩余量非负；
2. 所需 order/trade/cancel 引用完整；
3. 没有任何 ledger anomaly。

主动成交方向也在这里保守判定。必须同时观察到买卖引用，能确认较晚提交的一方，相关事件在序列上足够相邻，事前对手 BBO 可见，而且订单是市场单或可成交限价单；条件不足就返回未知，而不是用 vendor `side` 猜。

正式运行使用 `event_replay_mode=fused`：prestate 循环在“先拍状态、后改盘口”的同一遍回放中调用 lifecycle consumer，因此订单簿和生命周期共享一次事件扫描。代码还保留 `shadow` 模式，可把 fused 与旧的分开回放逐列精确比较；正式全历史使用已经验证过的 fused 路径。

#### 大白话解释

OrderBook 像“为了继续报路况，遇到坏记录也尽量往下走”；正式 ledger 像“审计账本，一分钱都不能擅自抹平”。两个系统同时存在并不重复：一个保证尽量还原市场状态，一个决定某张订单的研究证据是否真的可信。

原搓快照项目主要关心每个时点盘口能否继续恢复；当前项目进一步要求每张被统计的订单都能解释“原量最后去了哪里”。这是从行情重建走向行为研究新增的严谨层。

### 4.8 第八步：从一次回放构造 Pair、Chain、Cluster 和 Response

#### 技术原理

单张订单的生命周期只能描述“这张单撤了、成交了还是仍存活”。算法交易行为通常跨多张订单，例如撤单后改价重挂、把大单拆成连续子单、市场受到冲击后快速补单。要识别这些行为，需要把订单之间和动作前后建立联系。

当前 `ArtifactGraph` 会按 scorer 的依赖关系懒加载共享工件：同一股票日只构造一次 PRESTATE、LIFECYCLE、ORDER_PRESTATE、PAIRS 和 IMPACTS，需要它们的多个 scorer 复用同一结果，不允许每个因子各自重放一遍 L2。

#### 实际怎样实现 Pair

Pair 以旧订单的撤单子事件为核心，在撤单时点前后寻找同交易段、同方向、不同 `order_id` 的候选重挂单。新订单的原始提交必须晚于旧订单的原始提交，但允许区分 cancel-first、replace-first 和前后几乎同时的语义。

正式候选策略已经冻结为：

- 墙钟候选范围为 3 秒；
- 不另设 event-count 硬上限；
- 数量差使用对称 10% 硬门槛；旧单参考量在“本次撤单量”和“撤单前剩余量”中选择与候选新单更接近的一种；
- 普通连续竞价限价单要求价格 tick gap 可观察，但不设普通价格距离硬门槛；价格越远只会在连续核函数中得分更低；
- 市场单、特殊单或可成交限价单进入 special-marketability lane，必须能观察到事前对手 BBO，否则 fail closed。

候选通过硬门槛后，再用冻结参数计算连续相似度。代码中的结构可概括为：

```text
wall_similarity  = exp(-(abs_delta_time / theta_time) ^ p)
event_similarity = exp(-(abs_delta_seq  / theta_event) ^ p)
time_similarity  = sqrt(wall_similarity * event_similarity)

qty_similarity   = exp(-qty_log_distance / theta_qty)
price_similarity = exp(-tick_distance / theta_price)

edge_score = time_similarity ^ w_time
             * qty_similarity ^ w_qty
             * price_similarity ^ w_price
```

special-marketability lane 的价格项改用“相对事前对手 BBO 的可成交程度”，而不是把价格 0 当成真实 tick 距离。所有 `theta`、权重和 bundle hash 都来自冻结参数，正式历史计算不会重新估计。

Pair 候选数量可能非常大。正式运行使用 `pair_scoring_mode=stream`：候选按有界向量批次生成，`PairReducerSink` 只保留各活跃 scorer 需要的 local-best 或充分统计状态，不把数亿候选完整物化成 `pair_candidates` 文件。正式启动器在结束时还会反向检查输出目录，发现候选明细或 staging 残留就拒绝验收。

#### 实际怎样实现 Chain 和 Cluster

被选中的 Pair edge 形成订单图。`formal_chains.py` 用 union-find 找无向连通分量，生成确定性的 chain id；不会为了让链看起来更漂亮而临时增加最小节点数或额外阈值。每条链再计算：

- 根订单、尾订单、节点数和边数；
- edge score 的均值、20% 分位数和几何均值；
- 数量是否近似守恒；
- 改价方向、主动/被动价格变化和节省成本；
- reprice 比例、方向一致性和跟随 BBO 后的残差；
- 链证据是否完整。

另一类 aggressive cluster 从被严格识别为主动方的成交出发，在同方向上按墙钟/事件核连接连续子单，再统计到达间隔 CV、数量稳定性、深度消耗、市场响应和与市场总成交量的一致性。Pair/Chain 更像“撤单—重挂关系”，aggressive cluster 更像“连续主动执行关系”，两者不能混为一谈。

#### 实际怎样实现 Response

Response 观察一条动作怎样改变下一刻可见盘口。因为每个事件已经有 action-before prestate，当前事件应用后的状态可以由“下一个唯一事件的 prestate”得到。证据窗口最后一条事件没有窗口内的下一状态，因此不会凭空制造 poststate。

程序分别从买、卖方向评估：

- 本方/对手方 BBO 前进或后退；
- 队列稀释、对手深度消耗；
- 成交压力；
- 价差收窄或扩大；
- 盘口不平衡翻转；
- 短时波动跳升。

响应强度用事前 spread、深度等做归一化并限制在 `[0,1]`。正式运行的 `response_execution_mode=optimized` 预先建立列式索引和缓存，在冻结的 1 秒 lookback 中找动作和响应，避免每个 scorer 重复扫描 DataFrame；它仍然只使用 09:35 以前的 evidence，不向未来标签借状态。

#### 大白话解释

生命周期是给每个人做单独档案；Pair 是判断“两张单是否像一次撤单重挂”；Chain 是把一连串相关订单串成同一段执行；Response 是看这次动作之后市场有没有退让、补单或变薄。

原快照项目提供了“每一刻盘口是什么”的能力，当前项目在此基础上开始回答“谁可能在做什么、这些动作彼此是否属于同一段算法、市场如何回应”。技术地基相同，但研究对象从盘口状态升级成了行为关系。

### 4.9 第九步：把共享工件一次性归约成 495 列股票日因子

#### 技术原理

当前任务不是给每个 scorer 单独写一套读取、重放和聚合程序，而是先在订单轴上得到连续的行为证据，再统一映射成不同方向、不同上下文和不同机制的股票日统计。

正式分母固定为：

```text
D = 当天该股票在 [09:30,09:35) 内
    所有有效、去重的新委托数量
```

这个分母是 `all_valid_deduplicated_new_orders`，不是“某个因子恰好有非空值的订单数”。这样两个因子之间的数值差异表示行为强弱差异，而不是各自偷偷换了样本分母。

#### 订单级机制证据怎样形成

注册表把 50 个基础 scorer alias 分成四个机制家族：

| 机制家族 | 主要来源 | 直观含义 |
|---|---|---|
| Lifecycle（L） | `f01–f07` | 撤单、撤单比例、极短寿命、订单群、触及 BBO、部分成交退出等单订单行为 |
| Pair/Repost（P） | `f10–f21, f51, f52` | 撤单重挂、紧急改价、残量重挂、拆分/合并、成本与反转循环 |
| Chain/Cluster（C） | `f26–f41` 及 `c01–c03` 控制项 | 主动成交簇、子单序列、长链、重新定价、BBO 跟随、周期性和固定数量控制 |
| Response（R） | `f42–f47` | BBO 响应、队列稀释、深度耗尽、价差变化、失衡翻转和波动跳升 |

每个 scorer 给订单一个 `[0,1]` 连续强度，而不是只给 0/1 标签。每个家族取本家族 scorer 的逐订单最大值，得到 `L_i, P_i, C_i, R_i`；再取四者最大值得到算法联合证据 `U_i`。

四个 L2 consensus 不是新跑四套算法，而是对四家族证据做不同归约。将每张订单的四个家族强度从大到小记为 `s1 >= s2 >= s3 >= s4`：

```text
cons_union   = sum(s1) / D
cons_breadth = sum(L + P + C + R) / (4 * D)
cons_top2    = sum(s2) / D
cons_top3    = sum(s3) / D
```

`union` 高说明至少一种机制证据强；`breadth/top2/top3` 高说明同一批订单得到多种彼此不同的机制共同支持。

#### 28 个订单上下文怎样加入

L3 不是重新定义 28 种“算法”，而是把 `U_i` 与订单发生时的微观结构条件相乘，即 `U_i * x_{i,k}`。28 个 context 全部在统一事件轴上用一次前缀/滚动扫描得到，短窗 8 和长窗 32 指的是前 8/32 个事件，不是人为切 8 秒/32 秒时间桶。

| 编号 | 上下文 | 实际含义或公式 |
|---|---|---|
| x01 | spread wide | `max(spread_ticks-1,0) / max(spread_ticks,1)` |
| x02 | queue crowded | `qty_ahead / (qty_ahead + submit_qty)` |
| x03 | opponent thin | `submit_qty / (submit_qty + opponent_topN_depth)` |
| x04–x05 | book align / oppose | 本单方向与盘口不平衡同向或反向的正部分 |
| x06 | passive near-touch | 非主动单且处于本方 BBO 一档以内 |
| x07–x08 | stale quote 250ms / 1000ms | `1-exp(-BBO_age/0.25)` 与 `1-exp(-BBO_age/1)` |
| x09–x12 | OFI 8/32 align / oppose | 最近 8/32 事件订单流不平衡与本单方向同向或反向 |
| x13–x14 | trade flow 8 align / oppose | 最近 8 个事件的有符号成交流与本单方向关系 |
| x15 | aggressive | 事前 BBO 下的可成交程度 marketability |
| x16–x18 | depth consuming / sweep / instant fill | 复用正式深度消耗、多档扫单和即时成交诊断 |
| x19–x22 | microprice trend 8/32 align / oppose | microprice 短/长事件趋势与本单方向关系，按 spread/tick 归一化 |
| x23 | short volatility | `rms8 / (1 + rms8)` |
| x24 | recent jump | 前 8 个事件中最大的波动跳升强度 |
| x25–x26 | same/opponent book frontloaded | 本方或对手方 top-N 深度是否集中在最前档 |
| x27–x28 | same/opponent best thickness | 两侧一档量中，本方或对手方所占比例 |

上下文缺失时，正式矩阵把该项贡献设为 0，同时在 coverage matrix 中单独记录“不可观察”；不会用股票日均值填充，也不会把缺失当成强证据。

#### 12 个窗口状态怎样加入

L4 使用股票日在整个 `[09:30,09:35)` 的共同状态 `z_k`，构造 `U_i * z_k`。12 个状态为：

| 编号 | 状态 | 技术含义 |
|---|---|---|
| z01 | return skew signed | 窗口收益偏度，并用 `x/(1+abs(x))` 有界化 |
| z02 | excess kurtosis | 窗口收益超额峰度 |
| z03 | semivariance asymmetry | 上下行半方差不对称，保留符号 |
| z04 | path efficiency | 净价格移动 / 总路径长度 |
| z05 | max drawdown strength | 最大回撤按典型 spread 归一化 |
| z06 | trade price concentration | 用归一化熵描述成交是否集中在少数价格 |
| z07 | price-trade resonance signed | 成交方向与价格变化是否同向共振 |
| z08 | realized volatility | 窗口实现波动 |
| z09 | jump variation share | 跳跃变动占总变动的比例 |
| z10 | local count illiquidity | 价格总变动相对成交笔数和中位 spread 的大小 |
| z11 | average spread wide | 窗口 x01 均值 |
| z12 | average opponent thin | 窗口 x03 均值 |

有符号状态允许落在 `[-1,1]`，其余强度限制在 `[0,1]`，并同样单独保留 coverage。

#### 五种方向投影和 495 列怎样得到

对每个基础 scorer、每个 `U*x` 和每个 `U*z`，系统统一调用一次矩阵归约，生成五种投影：

```text
buy    = sum(买单贡献) / D
sell   = sum(卖单贡献) / D
total  = buy + sell
net    = buy - sell
absnet = abs(net)
```

方向未知的订单在 buy/sell 中贡献 0，不能被强行分到某一边。五个投影来自同一份订单矩阵，不会为 total、buy、sell、net、absnet 分别再重放一次订单簿。

最终列数严格由注册表决定：

| 层级 | 计算方式 | 列数 |
|---|---|---:|
| L1 | 50 个基础 scorer × 5 个方向投影 | 250 |
| L2 | union、breadth、second strongest、third strongest | 4 |
| L3 | 28 个订单 context × 5 个方向投影 | 140 |
| L4 | 12 个股票日 state × 5 个方向投影 | 60 |
| L5 | maker、taker、absorption、flow、withdrawal、resilience、herding、attention、contrast 等目的组合 | 36 |
| 诊断 | market fill、instant fill、depth consume、sweep、one-shot | 5 |
| 合计 | 490 个正式候选 + 5 个诊断 | **495** |

L5 的 36 列不是机械的五投影展开，而是用上述共享证据组合成更接近交易目的的量，例如做市刷新、对抗订单流、主动吃单、趋势执行、流动性吸收、撤单冲击、100/500/1000ms 补单韧性、羊群跟随/反向，以及 maker-minus-taker 等对比量。

构造完成后，程序逐个核对实际 factor id 与注册表：少一列、多一列、顺序不同或数值越界都会失败。495 列按每 block 最多 64 列写成 8 个 factor blocks；每个 block metadata 绑定 registry hash、窗口 identity、分母 schema、context schema 和本 block 列表，防止跨版本误拼。

#### 大白话解释

前面先给每张订单做了一套“行为体检”。这一层再把体检结果从三个角度汇总：它是什么行为、它发生在什么盘口环境、它发生在什么样的开盘 5 分钟行情里。最后按买卖方向统计成股票日的 495 个数字。

495 列并不意味着把 495 套程序各跑一遍。真正昂贵的 Doris 读取、事件排序、订单簿回放和生命周期只做一次；后面大部分列是对同一批订单级共享矩阵做向量化组合和归约。这正是当前项目相对原“逐时点搓快照”最重要的工程扩展。

### 4.10 第十步：在同一次日级调度中构造严格隔离的日内标签

#### 技术原理

因子回答“09:30–09:35 出现了什么行为”，标签回答“这些行为之后价格怎样变化”。二者可以共享原始 trade 查询，但必须在语义和执行依赖上隔离：先冻结因子，再计算未来收益；标签绝不能参与股票池选择或因子分母。

#### 实际怎样实现

`IntradayLabelPriceConsumer` 只读取 trade frame，并执行：

1. 优先按 `(channel_no, seq)` 去重；若缺少完整身份列，才使用 `data_time, price, qty, bid_id, ask_id` 等可用字段做后备去重。
2. naive 成交时间按上海本地墙钟解释，带时区时间转换到上海；只保留同一交易日、时间有效、价格和数量均为正且有限的记录。
3. 对通过校验的成交按 `data_time, channel_no, seq` 稳定排序。
4. 锚点价格取 **严格早于 09:35:00** 的最后一笔有效成交价：

```text
anchor_price = last(valid_trade where ts < 09:35:00)
```

5. 目标价取 `[09:44:00,09:45:00)` 内的成交量加权平均价：

```text
target_vwap = sum(price * qty) / sum(qty)
```

6. 正式收益标签为：

```text
ret_intraday_vwap_0944_0945_from_d1_0935_last
    = target_vwap / anchor_price - 1
```

边界审计会分别记录恰好落在 09:35、09:44 和 09:45 的成交数量。09:35 整点成交不能进入 anchor，09:44 整点可以进入 target，09:45 整点不能进入 target。锚点或目标区间没有合法成交时，标签为 `NaN`，不会向前填价格或伪造 0 收益。

调度器先注册 factor consumer，再注册 label consumer，并声明 label `depends_on_success_of` 对应 Open5m factor consumer。某只股票因子失败时，其标签任务不会绕过失败继续成为“看似完整”的样本。日级 finalizer 仍为股票池中的每个预期 code 生成一行，缺失标签保留 NaN，同时写入有效标签数、边界审计、spec hash、code revision 和 Parquet SHA256。

#### 大白话解释

因子像考生在 09:35 前交卷，标签像 09:44–09:45 才公布的成绩。系统可以让监考和阅卷共用同一批成交数据运输，但必须先把卷子封住，成绩才允许进入另一条处理链。没有成绩的考生仍然留在名单里，只是成绩记缺失，不能从样本中悄悄消失。

原搓快照项目用米筐 3 秒快照验证“盘口还原得对不对”；当前标签不是盘口真值，而是用于检验高频行为因子有没有后续收益解释力。两者都用到市场数据，但目的完全不同。

### 4.11 第十一步：日级原子提交、全历史评价和服务器保护

#### 技术原理

长任务真正的完成标准不是“Python 进程退出码为 0”，而是每个日期的股票池、因子列、标签、查询证据和文件哈希形成闭环。否则中途断电可能留下半个 Parquet，下一次运行又误以为当天已经完成。

#### 实际怎样实现日级提交

当一个交易日的所有股票任务成功后，`finalize_completed_day()` 才依次提交：

- 股票日 panel shard；
- 8 个 64 列上限的 factor blocks 及 block manifest；
- L2 availability 文件，区分股票池内代码是否有各表数据；
- query audit/telemetry；
- 当日 intraday label shard 及 label manifest；
- 绑定日期、股票池、参数、窗口、列、查询区间和代码版本的日级 telemetry manifest。

Parquet 和 JSON 都先写同目录临时文件，再用 `os.replace` 原子替换正式路径。只有 factor 与 label 所有日期都没有 failed date 时，才会生成 multiwindow `complete_开始日_结束日.json`，其中明确记录 `raw_extraction_shared=true`、消费者顺序、查询区间和每个窗口/标签的处理日期。

程序也实现了严格 resume，但它只是长任务的容错机制：只有 shard、telemetry、availability、列集合、文件哈希和当前 fingerprint 全部一致，某一天才允许被跳过；身份不一致就重新计算或失败，不能仅凭“文件名存在”认定完成。本次 354 日全历史已经全部提交并形成完整闭环；这里介绍 resume 只是在说明系统怎样保证长任务可恢复，不是在汇报当前计算进度。

#### 实际怎样做最终评价

`evaluate_open5m_count_proxy_bank.py` 从已经提交的 factor blocks 和同日 label shards 读取数据，先检查：

- 评价区间必须与 canary、Q2 或 full_history 冻结区间完全一致；
- 每个有因子 block 的日期必须有对应标签文件；
- factor id、registry hash 和唯一股票日键必须合法；
- 唯一允许的收益列就是冻结的 Open5m 日内 VWAP 标签。

随后对每个交易日、每个因子做横截面评价，至少需要 30 个有效股票：

```text
IC      = 当日因子值与收益的横截面 Pearson 相关系数
RankIC  = 当日因子排名与收益排名的 Spearman 相关系数
ICIR    = 日 RankIC 均值 / 日 RankIC 样本标准差
```

ICIR 不做年化；单日 canary 的标准差没有定义，因此 ICIR 必须保持 NaN，程序会拒绝“人为造出一个单日 ICIR”。full_history 评价除全区间汇总外，还会额外生成 2026Q2 比较期。最终写出 `daily_ic.parquet/csv`、`period_summary.parquet/csv` 和结果 JSON。

#### 实际怎样保护服务器任务

正式启动器在运行前检查：代码 revision 必须是精确 40 位 Git SHA、checkout 必须干净、输出目录与 scratch 目录必须为不同绝对路径、研究配置及冻结参数 SHA 必须匹配。正式计算使用：

- `run_guarded.py` 施加 100G 内存上限；
- heavy-task lock，避免同机多个重任务互相挤爆；
- 7200 秒 watchdog，并要求 CPU 持续有进展；
- 本地 `/tmp` 作为高频 progress hot root 和 Numba cache；
- 拒绝把 hot progress 放在 FUSE/NFS/CIFS/SMB3 上；
- 正式输出留在持久存储，并在结束后打包证据、计算 SHA256、核对最终 study result。

#### 大白话解释

每个交易日都像一个独立封箱：因子、标签、清单、哈希和查询记录全部装齐，才贴“完成”封条。断点续跑只认封条和箱内清单完全一致，不认地上有一个同名箱子。

原项目通过几只股票的图表、3 秒采样和米筐快照证明订单簿重建正确；当前项目把验证扩大到 354 天生产链：不仅要证明盘口逻辑正确，还要证明数据读得对、未来没有泄漏、每张订单数量守恒、495 列身份一致、每天完整落盘、全历史评价可以从成品独立重现。

## 五、与原“搓快照”项目相同的地方

### 5.1 原始市场事实相同

两者都从交易所的三类 L2 事件出发：

- 委托告诉我们新增了什么订单；
- 成交告诉我们哪些买卖订单被扣减；
- 撤单告诉我们原订单减少了多少剩余量。

不管最终要快照还是因子，最底层市场事实没有变化。

### 5.2 因果顺序相同

两者都以 `channel_no, seq` 作为核心事件顺序。`data_time` 用于判断自然时间和研究窗口，但不能代替 seq 的因果职责。

### 5.3 订单簿状态机相同

当前 `event_prestate` 仍直接复用 `snapshot.orderbook.OrderBook`：

- 委托增加订单账本和价格档位；
- 成交扣减买卖双方订单；
- 撤单扣减原订单；
- 市价单不作为 0 元固定档位挂入盘口；
- 盘口持续维护买卖价位聚合量。

这就是原项目最核心、最有长期价值的部分。

### 5.4 整数价格和交易所边界经验相同

价格仍以整数 tick/scale 表示；市价单、特殊订单、未知引用等边界仍要被明确处理。旧项目对这些问题的调查和验证，避免了当前因子系统重新踩一遍“0 元卖一”“订单引用不存在”等坑。

### 5.5 都强调验证不能只看一张图

旧项目曾经出现过验证器列名冲突导致“假一致”，因此建立了故意造错、验证器必须报错的防回归测试。当前系统延续了同样的原则，只是验证对象从快照一致性扩展为：

- 事件顺序和数量守恒；
- 窗口边界与未来隔离；
- 每日每表查询次数；
- 因子列、registry 和 schema hash；
- resume 身份；
- 资源和最终结果 manifest。

## 六、与原“搓快照”项目不同的地方

### 6.1 任务目标不同

| 原项目 | 当前项目 |
|---|---|
| 证明盘口能够被正确还原 | 研究订单行为能否形成有效因子 |
| 快照本身是核心产品 | 盘口状态只是因子输入之一 |
| 重点是订单簿价量是否正确 | 重点是订单生命周期、关联行为、市场响应和未来收益 |

### 6.2 数据载体和运行环境不同

| 原项目 | 当前项目 |
|---|---|
| 本地 E 盘、MT 拷贝的 Parquet | 公司服务器 Apache Doris L1+L2 |
| 本地电脑、单票/少量日期 | 服务器 16 核/128 GiB 配额、全市场多日任务 |
| 路径写在 Windows 工作区 | 环境变量解析 repo/output/scratch，服务器路径与本地路径分离 |

### 6.3 时间字段语义发生了重要变化

旧本地 Parquet 的说明是 `data_time` 按 UTC 存储，再转北京时间。

服务器 Doris 的 `DATETIME` 已实测为**不带时区标签的北京时间裸值**。因此当前规则是：

- naive 时间原样解释为北京时间；
- 只有明确带时区的输入才转换到 `Asia/Shanghai` 后去掉时区标签。

如果机械照搬旧规则，对 Doris naive 时间再次执行 UTC→上海转换，会整体多加 8 小时，把 09:30 的事件变成 17:30，整个开盘窗口都会被移空。这是迁移后最重要的数据语义修正之一。

### 6.4 “拍照时点”不同

原快照在网格时刻 `t` 消费 `event_time <= t` 的全部事件，输出的是时刻 `t` 已发生事件之后的状态。

当前 prestate 在每条动作发生前记录状态，然后再应用当前事件。它回答的是“这张订单做决定时面对什么市场”，因果语义更适合因子研究。

### 6.5 输出粒度不同

原项目每只股票每天产生大量 100ms 行；当前正式面板最终通常每只股票每天一行，把窗口内大量事件归约成数百个因子值。

因此当前磁盘空间主要用于生命周期、因子 block、panel、label、报告和 manifest，而不是全市场高频盘口快照。

### 6.6 参考数据和正确性证明不同

原项目使用米筐 3 秒 L2 快照作为外部参考，通过 100ms/3s 自洽和累计成交量对齐证明盘口正确。

Open5m 正式任务没有再按日生成 3 秒快照去和米筐做三方对比。米筐验证属于历史正确性证据和回归基础；这次服务器计算与最终验收关注的是数据库访问、窗口泄漏、数量守恒、因子定义和全历史产物是否闭合。

### 6.7 当前市场范围更窄但股票数量更大

原项目用深圳 `000001` 和上海 `600000` 各 7 日验证沪深差异。当前 Open5m 正式研究只覆盖深市普通股，因此上海主动单缺少独立委托、上海时间戳等专项逻辑不在当前主任务的实际研究范围内。

虽然市场从沪深两市缩到深市，但股票数量和日期数量从两个样本扩展到了全深市、354 个正式交易日，任务规模反而大得多。

### 6.8 集合竞价的角色不同

旧项目需要在开盘和收盘集合竞价阶段输出指示性成交价、匹配量和不平衡量。

当前 Open5m 只把 09:30 前事件作为恢复开盘订单簿的 context，不输出旧的集合竞价指示性快照。`auction.py` 仍保留在 snapshot 项目中，但不是当前 Open5m 因子主链的计算环节。

## 七、原搓快照项目的哪些部分正在被复用

可以按复用强度分成四层。

### 7.1 直接代码复用：最核心

1. `snapshot.events.build_event_stream`：三表标准化和事件排序；
2. `snapshot.orderbook.OrderBook`：订单账本与全深度盘口；
3. 整数价格、side/order type 标准化；
4. 委托、成交、撤单的状态更新规则。

当前 AlgoBench 的 `event_prestate` 会直接 import 并实例化这个 OrderBook，不是重新写了一套名字相似的实现。

### 7.2 算法思想复用：从定时快照演化为事件快照

原来是“连续维护状态，到了网格点就拍照”；现在是“连续维护状态，每个动作发生前就取一次所需字段”。

两者都依赖同一个连续状态，只是取样方式不同：

- 100ms 快照适合生成行情产品和可视化；
- action-before prestate 适合研究订单决策的因果环境。

### 7.3 工程框架复用并扩建：迁移后新增

`lv2_snapshot_workspace` 现在不仅包含快照代码，还成为全仓库唯一的 L2 数据基础设施，新增了：

- `snapshot.io` Doris 网关；
- `snapshot.query_plan.QueryPlan`；
- `snapshot.scheduler.DailyScheduler`；
- PyArrow 流式解析；
- 查询遥测和存储策略。

这些不是 6 月 25 日原版本已有的功能，但它们建在原 snapshot 包和数据契约之上，供 snapshot、lowlat、clusterlob 和 algobench 共享。

### 7.4 间接复用：下游只消费结果

当前和后续任务对旧能力的依赖程度并不一样：

| 当前任务部分 | 对原搓快照能力的复用方式 |
|---|---|
| Open5m 因子面板 | **强直接复用**：事件合并、OrderBook、动作前盘口、成交状态 |
| 生命周期/Pair/Chain/Response | **扩展复用**：建立在正确事件流和盘口上，但新增了独立数量账本和行为关联算法 |
| 日内收益标签 | **部分复用**：主要复用成交排序、累计量和边界状态，不需要订单簿深度 |
| IC/RankIC 评价 | **间接复用**：读取已经生成的股票日因子和标签，不再回放订单簿 |
| 后续 127 因子 ML | **更下游的间接复用**：只读取完整 factor blocks 和 labels，不访问 L2、不重建盘口 |
| 本地 open3m 跨日比较 | **精简直接复用**：新增两个成交边界状态，用累计额/量差计算 `[09:30,09:33)` VWAP |

## 八、当前明确没有继续复用的旧链路

以下能力仍保存在 snapshot 项目中，但没有进入当前 Open5m 服务器正式任务：

- 每 100ms 固定网格生成全日快照；
- 单独生成 3 秒快照；
- “我的 100ms / 我的 3s / 米筐 3s”三方对比；
- `rqref.py` 米筐快照缓存；
- 按累计成交量对齐米筐的日常验收；
- 全市场快照宽表和三方重合图；
- 上海 `600000` 样本及上海专项验证；
- 集合竞价指示价作为当前因子输出。

不能因为这些环节不在当前主链，就说旧项目没有复用。恰恰相反：它们完成了早期正确性证明，使最重要的状态机可以被放心地放到更大规模、更复杂的因子系统下面。

## 九、当前项目最容易混淆的几个概念

### 9.1 “用了 L1”不等于“不再重建订单簿”

L1 负责股票池、交易日、日线、复权和规则参考；L2 负责逐笔订单和真实盘口。当前两者同时使用，各自承担不同职责。

### 9.2 “没有输出 100ms 快照”不等于“没有盘口状态”

当前系统仍然连续维护盘口，而且会为每个有效动作提取更细的事件前状态。只是这些状态主要作为中间特征，不再全部按时间网格落盘。

### 9.3 “495 列因子”不等于“495 套算法”

495 列共享同一次事件回放、同一生命周期、同一 Pair/Chain/Response 和同一组上下文矩阵。很多列只是同一证据在不同方向或市场状态下的投影。

### 9.4 “服务器数据更多”不意味着可以放松边界

数据规模越大，越需要严格限制：单日 SQL、明确字段、时间半开区间、未来隔离、原始数据不落盘、完整日 resume 和最终 manifest。否则一个小错误会被复制到数百万股票日中。

## 十一、当前阶段的正确理解

当前阶段不是在“重新做一遍 6 月 25 日的快照项目”，也不是简单地“把本地代码复制到服务器跑”。真正发生的是三层升级：

1. **数据层升级**：本地 Parquet 变成公司 Doris L1+L2，建立严格的 SQL、时间、存储和权限边界；
2. **表示层升级**：100ms 定时快照变成事件级 action-before prestate，并增加正式生命周期、FIFO、Pair、Chain 和 Response；
3. **研究层升级**：从验证盘口正确，升级到构造全市场股票日因子、检验未来收益并准备机器学习数据源。

最准确的总结是：

> 6 月 25 日完成的是“把逐笔流水还原成可信市场状态”的基础工程；迁移到服务器以后，项目已经进一步完成了“把可信市场状态和订单行为压缩成可评价、可复用的全历史因子数据”。原来的订单簿重建引擎仍在这套系统最底层工作，但固定 100ms/3s 快照已经不再是服务器 Open5m 主任务的中间产品。旧项目从一个独立成品，变成了当前整个高频因子研究体系的基础设施。
