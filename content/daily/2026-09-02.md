# 新因子机制预查提速：单日计算从 206.49 秒降到 29.91 秒

## 1. 当前结果

本轮任务检查深交所全市场开盘前 5 分钟的 L2 订单行为，覆盖六个 P0 诊断项：`C1.1`、`C1.3`、`C1.4`、`C3.2`、`C3.3` 和 `C7.1`。

当前最快版本为 `e08427701c6aef0bb65c5baacbd3e50a1889fb13`。固定交易日 `2026-04-01` 的一次完整冷启动实测为：

```text
端到端耗时：29.909839450381696 秒
性能上限：30.0 秒
剩余余量：约 0.09 秒
峰值 RSS：9,528,082,432 bytes，约 8.87 GiB
随机对照次数：0
```

计时从首次查询 L2 数据之前开始，到机器表、HTML、`PRESCREEN_RESULT.json`、阶段指标和 SHA-256 证据全部写完并校验通过为止。

本次共读取 27,304,427 条 L2 记录，规范化后形成 13,165,606 条订单记录。七项正确性检查全部通过，actual-only 版本各轮的核心业务产物哈希一致。

当前版本只完成了一次正式冷启动实测。因此，现有证据可以证明这一轮运行进入 30 秒，但还没有完成“两次独立冷启动均不超过 30 秒且时间差不超过 5%”的稳定性验收。

## 2. 三个可比较的时间点

| 版本和任务口径 | 端到端耗时 | 说明 |
|---|---:|---|
| `aea0e6c`，完整 research null，199 次随机对照 | 206.49 秒 | 包含真实统计和 199 个随机对照世界，`research_nulls` 单独耗时 88.03 秒 |
| `171a471`，actual-only 初版 | 38.95 秒 | 按当前研究口径删除全部随机对照，只保留真实分布统计；当时解析和规范化仍需 11.45 秒 |
| `e084277`，当前 actual-only 版本 | **29.91 秒** | 在同一 actual-only 业务口径上继续优化查询、解析、共享状态和三个候选计算阶段 |

从 199 次随机对照版本到当前版本，端到端时间减少约 85.5%，速度约为原来的 6.9 倍。这里最大的变化来自研究范围调整，不能全部解释为同工作量下的代码提速。

在可直接比较的 actual-only 口径下，端到端时间由 38.95 秒降到 29.91 秒，减少约 9.04 秒，降幅约 23.2%。

## 3. 当前任务实际在做什么

这项预查不读取未来收益，也不计算 IC。它只看订单、成交和撤单本身，描述真实市场里是否存在下面几类形状：

- `C1.1`：委托数量和价格相乘后，金额是否集中在常见整数网格附近；
- `C1.3`：委托数量是否偏好被 2、5、10、20、50、100 等整数整除；
- `C1.4`：远离当前同侧最优价的被动委托，价格末位是否集中在某些数字；
- `C3.2`：同一交易通道的相邻序号中，是否频繁出现不同股票；
- `C3.3`：不同股票是否在很短时间内出现相同委托数量；
- `C7.1`：主动订单的成交量是否恰好耗尽提交前最优档深度，或继续穿透下一档。

由于随机对照已经取消，结果只能描述频数、占比、尖峰位置、覆盖率和跨日持续性。当前产物不能把原始尖峰解释为统计显著性、因果机制或算法身份，候选状态只允许 `diagnostic_only` 或 `not_run`。

## 4. 当前版本保留的提速手段

本节只记录 `e084277` 当前生产路径仍然使用的做法。已经撤销、无全市场收益或只服务于旧随机对照任务的实验不计入当前方案。

### 4.1 取消 199 次随机对照

当前任务固定为 `actual_only`，`randomization_replicates: 0`。程序不再生成置换、循环平移、重配对等随机样本，也不再计算 null 均值、99% envelope、excess 和 actual/null ratio。

这一决定直接删除了原来 88.03 秒的 `research_nulls` 阶段，同时减少了随机样本准备、排序、分组、GPU/CPU 计算和 `null_summary.parquet` 写入。`actual_summary.parquet` 取代了 `null_summary.parquet`。

这是研究范围调整，不是单纯的实现优化。相应的解释边界已经写入 `decisions/2026-09-03-actual-only-new-factor-prescreen.md` 和预注册文件。

### 4.2 把过滤条件尽量下推到 Doris

查询只覆盖冻结的深交所 0/3 开头股票池，避免先把其他市场或不在样本中的股票传到 Python 再丢弃。

三张 L2 表都把 `09:35:00` 的结束边界下推到数据库。订单簿重建需要 09:30 前的历史事件作为开盘时状态，因此查询不能简单地从 09:30 开始；当前实现保留开盘前上下文，但不读取 09:35 之后的数据。

最终一次运行中，三表读取量为：

| 表 | 查询数 | 行数 | 读取字节 | 该表完成时间 |
|---|---:|---:|---:|---:|
| order | 2 | 15,815,871 | 1,070,007,843 | 21.44 秒 |
| trade | 2 | 8,594,944 | 615,659,008 | 13.67 秒 |
| cancel | 1 | 2,893,612 | 162,326,650 | 8.19 秒 |

### 4.3 查询分片，并让三表同时读取

order 和 trade 各按股票池拆成两条互不重叠的流，cancel 保留一条流。每张表的分片并集必须恰好覆盖冻结股票池，不能重复读取，也不能漏股票。

order、trade、cancel 三表同时查询。端到端等待时间取决于最慢的 order 流，而不是三张表耗时相加。当前 `l2_query_extract` 为 21.45 秒，吞吐约 127 万行/秒。

查询侧固定 `table_parallelism: 3`，每条查询只给一个 parser 线程。这样能让多条流并行，又不会让每条流内部继续开线程，造成 CPU 超额订阅。

### 4.4 边查询边构建股票状态

程序不等 27,304,427 条记录全部收齐后再开始后续工作。每只股票的数据流准备好后，就提交给生命周期和盘口回放 worker。

因此，数据库读取、解析和股票级状态构建会发生时间重叠。进程池启动也与流式查询重叠；任务尾部释放 replay worker 时，主进程继续做候选汇总和报告准备，不单独等待清理结束。

### 4.5 缩小 pandas 的职责

当前版本没有完全移除 pandas。性能配置仍是 `parser_backend: pandas`，查询结果、少量表结构校验和最终 Parquet/HTML 组装仍使用 DataFrame。

真正的大数据计算已经尽量离开 pandas：

- 时间戳转成连续的 `datetime64[ns]` 或整数时间数组；
- 买卖方向和订单类型编码成 `int8`；
- 订单号、通道号、序号、数量和价格 tick 使用定长整数数组；
- 字符串只在边界处解析一次，热循环不反复 decode；
- 分组、排序、查找、分箱和计数使用 NumPy/Numba/CUDA；
- 只在最终输出只有几十或几百行时重新组装 DataFrame。

这相当于让 pandas 负责“接数据和交结果”，让 NumPy、Numba 和 CUDA 负责数百万行上的重复计算。

### 4.6 只规范化真正需要的字段

订单规范化不再复制整张宽表。程序只保留六个候选和共享状态真正会读取的列，并在第一次转换时确定类型。

同一份数值编码会被 C1、C3 和共享生命周期复用，避免每个候选重新执行 `astype`、字符串映射、日期分类和订单号转换。actual-only 初版的 `parse_normalize` 为 11.45 秒，当前为 2.69 秒。

### 4.7 每只股票的事件只构建一次

订单、成交和撤单先合成一份规范事件序列。生命周期、下单前盘口和执行几何从这份共享事件状态派生，不再为每个候选重复排序、合并和回放。

worker 直接返回紧凑的 typed arrays 和候选所需状态。主进程复用这些数组，不再把大型 DataFrame 在进程间来回序列化。`shared_lifecycle_prestate` 当前只需 1.41 秒。

### 4.8 固定 16 个股票级 replay 进程

股票之间没有计算依赖，服务器使用 Linux `fork` 创建 16 个长期进程，按股票并行重建生命周期和下单前盘口。

每个 worker 的内部线程固定为 1，Numba/BLAS 线程数受统一 CPU quota 管理。这样不会出现“16 个进程，每个进程又开十几个线程”的竞争。

进程池任务传递的是轻量索引和共享只读数据，减少 pickle、内存复制和进程通信。

### 4.9 C1：数值数组一次编码，多种统计一起复用

C1 的三个诊断原来容易分别转换数量、价格、订单类型和分层标签。当前版本先生成数值编码，然后复用到金额网格、整数整除谱和远价末位统计。

主要做法包括：

- 用向量运算计算数量、价格 tick 和金额网格距离；
- 用广播和整除运算一次生成多个 divisor 的命中矩阵；
- 用直方图和分箱代替逐行累加；
- C1.1、C1.3、C1.4 的独立 actual histogram 并行执行；
- Numba 内核在 L2 数据仍在流式读取时预热，把 JIT 首次编译藏在数据库等待时间内；
- 复用 `side_code`、`order_type_code`、价格层和订单号的数值表示。

最终 `c1_order_fingerprint` 为 1.15 秒，其中金额网格约 0.31 秒、整除谱约 0.89 秒、远价末位约 0.08 秒。子步骤存在并行和共享准备，不能把三项机械相加当成阶段总耗时。

### 4.10 C3：排序复用、线性扫描和 GPU 配对计数

`C3.2` 和 `C3.3` 都依赖全市场订单的时间、通道、股票和数量。当前版本只准备一次紧凑布局，然后分别计算相邻序号和同数量短时配对。

主要做法包括：

- 复用已经排好的通道、序号和数量顺序；
- 相邻序号统计改为连续数组上的线性扫描；
- 同数量配对先按数量形成连续分组，只在组内比较时间邻域；
- 用边界索引、窄整数列和压缩后的重复事件减少排序工作区；
- 复用 GPU buffer，在 CUDA 上完成实际同数量配对直方图；
- C3 layout 的准备与生命周期产物组装同时进行；
- C3 和其他互不依赖的 actual scan 并发执行。

`c3_cross_stock_scan` 从 199 次随机对照版本的 12.21 秒降到当前 0.13 秒。两者工作量不同；当前数字代表 actual-only 的真实统计路径。

### 4.11 C7：在共享回放中直接生成执行几何

主动订单是否恰好吃完最优档，需要提交前盘口和订单成交汇总。当前实现把这项判断放进共享事件回放：

- 用数值订单键关联订单和成交，不反复做 DataFrame join；
- 一张主动订单的多条成交消息先汇总，再只贡献一个观察；
- “耗尽、被挡住、穿透、不可判定”使用数组条件一次分类；
- 主阶段直接接收 worker 生成的 geometry 结果，不再二次扫描全表。

因此计时表里的 `c7_execution_geometry` 只有约 0.00005 秒。主要工作已经计入 `shared_lifecycle_prestate`，这个极小数字不表示四百多万条记录可以凭空在几十微秒内重新计算一遍。

### 4.12 独立工作并发，公共工作只做一次

当前调度同时遵守两条原则：

1. C1、C3、生命周期回放等互不依赖的工作尽量并发；
2. 事件排序、数值编码、股票分组、生命周期和盘口状态等公共工作只构建一次。

order 数据流还会按用途拆给规范化、C1 预处理和 C3 布局准备，避免所有任务排成一条长串。最终的 C3 布局准备与产物组装重叠，是 `e084277` 的最后一项有效改动。

### 4.13 小结果才写盘，写完立即校验

运行期间不保存数百万行的中间明细。程序只写候选摘要、形状分箱、逐日持续性、Top 模态、质量信息、HTML、阶段指标和证据哈希。

最终写入量为 90,802 bytes，`write_render_validate_hash` 为 0.60 秒。文件写完后立即做 schema、数量守恒、报告可追溯和 SHA-256 校验，避免为了追求速度省掉正式验收。

### 4.14 用阶段计时和固定资源定位真正瓶颈

任务固定记录 L2 查询、解析、共享状态、C1、C3、C7 和写入校验七个阶段，并继续细分 C1/C3 热点。每轮使用同一交易日、同一股票池、同一窗口、同一 CPU 配额和全新输出目录。

固定资源和细分计时本身不会直接减少计算量，但它能区分数据库等待、pandas 解析、进程通信、数值内核和文件写入，避免根据总时间猜瓶颈。

## 8. 全时间计算的接续边界

下一阶段要把同一套 actual-only 统计扩展到 `2024-01-01` 至 `2026-06-30` 的全部有效交易日。当前 `scripts/run_open5m_new_factor_prescreen.py` 仍会主动拒绝 `full_history`，所以全时间任务不能只改命令行参数，必须先实现按交易日运行、分日提交、失败恢复和全期归约。

全时间实现应保持以下条件不变：

- 六个候选及其统计定义不变；
- `actual_only` 和 `randomization_replicates: 0` 不变；
- 每日证据窗口仍为 `[09:30:00,09:35:00)`，并保留下单前盘口所需的开盘前上下文；
- 不读取任何未来收益或 IC 标签；
- 每日结果按 revision、registry hash、日期、股票池和 schema 校验后才能 resume；
- 失败日期可单独重跑，已验证日期不重复计算；
- 全期结果按 2024、2025、2026H1 分栏汇总；
- 最终仍生成机器表、HTML、质量检查、阶段指标和 SHA-256 证据；
- 当前单日快路不因全时间调度改造而改变计算口径。
