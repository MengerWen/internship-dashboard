# 深市全市场预检提速全记录：227 日实测 47 分 05 秒

**227 个交易日、深市全市场、逐股 88 个截点，完整实测 47 分 05 秒。** 11 月 23 日立项时，目标是把 200 多日压到 8 小时内。第一阶段完成六个全池日，按后段较慢日给出 **5 小时 20 分钟**的排期。目标随后收紧到 1 小时。11 月 24 日凌晨，最终版从空结果目录重新取数，全部 227 日完成计算、签收和公司 S3 回读，含资源 guard 起止共 **2,824.62 秒**，比 1 小时门槛提前 **12 分 55 秒**。 [六日实测与八小时排期][eight-hour] · [227 日完整实测][one-hour]

单日对照里，负载最重的补充日期 2026-07-02 保持 **323,909,610** 条有效逐笔和相同的逐股结果，采集由 **80.06 秒降到 39.21 秒**。先让查询少重读，再缩短每页传输，最后用多个日期填满经过实测的共享工位。作为起点，固定扩样中的 C++ 入口同口径比 Python 入口快 **1.19 倍**。

## 一、计算对象与计时口径

### 1.1 每个交易日实际交付什么

227 日由原有 200 个市场状态样本及按同一规则补充的 27 日组成。每个日期读取当日 L1 深市 A 股池，再按日期和股票代码范围提取 Doris 的委托、成交、撤单三表。每个股票日计算 88 个时间截点上的累计委托、成交、撤单，以及同股同侧的一秒内撤单后新委托机会。三段盘外计数、重复序号、找不到原委托的撤单和缺数状态随逐股收据保留。三表为空的股票也在当日覆盖表里。

同侧撤后新委托机会用于衡量盘中事件和配对工作量。这里交付的是**负载预检**。长窗 344 列因子生产、全期定参和模型训练各有自己的输入、求解和验收流程，其工期仍由对应链路的实测决定。扩样代理、全天工期情景及截点含义可对照 11 月 22 日的负载预检。 [预检计划][plan] · [分层扩样与工期情景][expanded]

## 二、先把抽样预检改成有界的 C++ 取数和计数

固定扩样是 24 日、每个日期取 4 只分散股票。每个代码点要发三表查询，单轮共 288 条 SQL。计数只占一部分墙钟，分散代码的首字节等待和查询往返重复了许多次。密集代码段则有另一种浪费。页宽过大会读到预算上限才被截断，之后再拆成两个子页，父页已传输的行得重读。

独立 C++ 采集器沿用同一份 _szse_intraday_counts_ 计数库。_ResearchGateway::read_ 继续用 _doris_select_ 和 _bounded_page_read_ 生成窄字段查询、申请共享工位和执行分页预算。采集器把窄 TSV 解析、按股分组和有类型列的构造合在一遍。相邻代码在有界范围内成页，按已完成页负载修正后续页宽。多股页超预算先按代码二分，单股仍超预算再按时间二分。完成页保持 100 万行和 64 MiB 上限，代码范围中的非股池代码在本地过滤。

## 三、两条共享工位下，让取数和逐股计数同时做

### 3.1 上一页交给计数，下一页开始查询

整日全池约有 2,900 只股票。一页三表读完后，如果等待该页所有股票算完才派发下一页，Doris 工位会在本地计数期间空下来。股票之间的消息量差异也大，静态分组会把同组其他股票排在重股后面。

_collect_ 在本页读完并更新下一页宽度后立即补发查询，把当前页交给 _count_stocks_。计数线程动态领取股票，初版默认最多六个 worker。每只股票仍通过 _stock_receipt_ 使用同一个计数库。最后按股票代码顺序写出收据并处理异常，同一页有多处冲突时仍报告代码顺序上的首个失败。账户 SQL 上限仍为两路，每页仍有行数、字节数和超时限制。 [分页与计数重叠的改动][overlap]

## 四、一小时目标先从少读数据开始

### 4.1 在相同页形下对照第三条 SQL 工位

重负载日 2026-07-02 保持股池、计数库和范围页策略，第三个查询 worker 继续申请项目现有账户共享工位。采集 **80.06 → 74.46 秒**，查询数仍是 1,016，超预算重读和过滤仍约 1 亿行。第三路能覆盖一部分等待，页划分带来的返工还在。

### 4.2 用当日 L1 成交笔数预估代码页负载

仅按相邻页反馈调宽，第一批遇上重股时仍可能先发一个过大的页，对下一批股票的密度也只能事后修正。_workload_width_ 先读取当日每股 L1 成交笔数，沿已冻结的代码顺序累加权重，到页的代理预算就切开。成交多的股票用窄页，轻股票可并页。L1 只是安排页宽的预估量。每只股仍查完整的 L2 三表，零成交、无 L2、极端重股和编码间隙继续由原始股池覆盖及分页检查处理。

重日采集 **74.46 → 56.83 秒**，查询 **1,016 → 851 条**，多读或过滤 **1.000 亿 → 2,200 万行**，减少约 **78%**。这一轮最大的收益来自父页截断后少重读。当天输入仍为 323,909,610 条有效逐笔。 [L1 引导页代码][weighted]

### 4.3 委托、成交、撤单各自切页

共用页边界会被最密的表约束。委托表需要小页时，成交表和更稀疏的撤单表也跟着分成许多小查询。程序先划出一个有限大小的逐股计数块，_DayInput::fetch_ 再在块内为各表独立切页。代码以约 240 万 L1 笔数为块级代理预算，委托、成交和撤单的页级代理预算分别为 52 万、88.5 万、175 万 L1 笔数。实际页仍由共同的行数、字节和二分规则约束。三表读完后按股票对齐，再交给同一段计数代码。

2026-07-02 采集 **56.83 → 48.45 秒**，查询 **851 → 585 条**，减少约 **31%**。多读或过滤仍约 2,200 万行，收益主要体现在减少查询和页交接次数。 [三表独立分页代码][table-pages]

## 五、在现有 MySQL 端口缩短每页传输

现有端口上的 zstd、zlib 协商试验均失败。已验证的路径使用 MySQL 原生客户端执行预处理语句，由服务端返回二进制结果。_doris_prepared_mysql_ 将返回值按原字段顺序输出为窄 TSV，交给原网关和采集器。保留了现有登录、窄投影、共享工位、行／字节准入、超时、分股解析和计数。这里提速的是传输环节，采集器仍用原有解析入口。

先在三表小页逐行核对文本与二进制指纹。再用同一密集样本按文本、二进制、二进制、文本交替采集，每次 **18,466,238 行、32 条查询**，分别用时 **3.12、2.31、2.39、2.82 秒**，逐股科学指纹相同。最后回到相同重日，三表独立页都是 **585 条查询**、约 **2,200 万行**多读或过滤，采集 **48.45 → 39.21 秒**。这组前后对照隔离了查询形状变化，保留了 Doris 的自然波动。 [二进制客户端改动][mysql] · [配对行数与指纹][one-hour-evidence]

### 6.2 查、算、写三个阶段有界交接

最终批次同时采集最多三个日期。每个日期进程最多三个查询 worker 和三个计数 worker，所有查询一起争用八条账户工位。已知日期按 L1 笔数总量从大到小派发，先处理可能拖长末尾的重日。两个发布 worker 与采集重叠，采集与待发布日期合计最多五个。每个独立采集进程结束即释放页数据和计数内存。

调度器复用原生采集器以及 _ObjectPublication_。采集结束后核对日期、股池、计数库和逐股覆盖，再压缩日级派生载荷，上传并从公司 S3 回读完整对象，确认 SHA-256 后写入日级完成收据。全批按日期汇总 88 个截点，并再次读回汇总对象。原始逐笔在内存处理，持久保存的是冻结输入、逐股派生结果、签收和汇总。

### 6.3 工位配置和断点恢复进入验收

整期按八个工位验证，启动时记录并核对账户实际工位数，运行中检测其变化。变化后停止派发新日期，已经在途且通过核验的对象仍可签收。参考日指纹从已签对象生成，采集前检查为合法 SHA-256，算完对照日再核对实际指纹。前两次整期尝试分别遇到六路变三路和参考指纹误录，都保留了已签日期。正式 227 日测速另用空输出目录。

恢复以执行版本、二进制、冻结日历、股池与 L1 身份、运行参数、日期和持久对象哈希核对，通过的日期直接复用。四、六、八工位三次 12 日恢复试跑分别用时 **1.55、0.70、1.39 秒**，新增采集均为零。恢复时间单列，首次完整测速计入全部 227 日重新采集。 [批次发布与恢复入口][campaign] · [指纹与执行身份检查][accepted-build]
