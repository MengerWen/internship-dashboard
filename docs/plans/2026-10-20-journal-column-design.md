# 新栏目「研究日志」构思方案

记录日期：2026-10-20。本文只做方案构思，不改 `site/`、`build.py`、`content/` 或任何构建逻辑。文中的天数、提交数、PLAN 数来自本机三个仓库与 `content/daily/` 的实测统计，统计口径写在第 3 节。

---

## 1. 这个栏目要解决什么

现有两栏各自回答一个问题：

- **正式成果**：这个项目做成了什么。六个阶段，结论导向，面向导师、面试官。
- **每日汇报**：某一天得到了什么结论。长文、图表、证据链完整，面向汇报与复盘。

缺的是第三个问题：**这些成果是怎么一天一天推进出来的**。现在只有 35 天有汇报，而实际有工作记录的日子是 91 天。中间 56 天的工作——提速、审计、修根因、搭环境、清存储——没有任何地方体现，但它们恰恰是把一个结论推到下一个结论的那部分。

所以新栏目的定位是**过程**，不是成果：

| | 单位 | 回答 | 文字量 |
|---|---|---|---|
| 正式成果 | 阶段 | 做成了什么 | 长 |
| 每日汇报 | 一篇报告 | 这天的结论是什么 | 长 |
| 研究日志 | 一天 | 这天干了什么、接住了什么、交给了谁 | 一句话 + 可展开 |

这条分工决定了后面所有取舍：**日志的每日正文必须短**。它是索引和脉络，不是第二套日报。长内容的去处已经有了（每日汇报），日志只负责把 91 天串成能读的线。

## 2. 栏目名

顶栏现在是「正式成果」「每日汇报」，四字 + 四字。第三个保持四字，版式节奏不破。

| 候选 | 说法 | 不选的理由 |
|---|---|---|
| **研究日志**（推荐） | 「日志」是过程记录，与「汇报」（结论）天然区分；「研究」保持档案的语域 | — |
| 推进日志 | 直接点出「交接推进」这层意思，和链条设计最贴 | 「推进」偏管理口径，和站点其他文案不同调 |
| 工作日志 | 最贴近「我每天干了什么」 | 读起来像考勤表，削弱研究档案的可信度 |
| 研究轨迹 | 强调线与轨 | 「轨迹」偏抽象，第一眼不知道点进去看什么 |

推荐 **研究日志**。视图内标题用「研究日志」，副题一行写清它是什么：**每天做了什么，接住了什么，交给了谁**。英文小字沿用现有 masthead 习惯（`Research Log`）。

## 3. 现有素材盘点（实测）

统计口径：三个 git 仓库 `git log` 的作者日期，加 `content/daily/*.md`（排除 `.show.md`），加研究仓库 `PLAN/*.md` 的文件名日期；窗口 2026-06-01 起。

- **有记录的日子：91 天**，2026-06-23 → 2026-10-20，仍在继续。
  （初次统计是 92 天、从 2026-06-04 起；加上按仓库限定子树的白名单后，2026-06-04 整天只剩别家公司的笔试提交和一个仓库根文件，不属于本实习，整天移出。）
- **提交：约 2715 次**，分布在三个仓库：
  - `sirui-quant-research` 2455 次（研究主仓，2026-07-14 起）
  - `Quant_Research-Trading` 142 次（父仓，6–7 月为主）
  - `internship-dashboard` 118 次（本看板仓）
- **每日汇报：35 篇**，覆盖 91 天中的 38%。其中 3 天有汇报但当天没有提交：2026-07-05、2026-08-01、2026-09-16。
- **PLAN 文件：157 个**，其中 129 个带日期前缀，分布在 50 天。
- 单日提交量从 1 次到 243 次（2026-08-18）。

两个由此确定的事实：

**一、提交粒度远细于「一天干了什么」。** 提交信息本身质量很高（单一目的、中文陈述句），但 161 条「复用自有解析容器恢复完整日清单」这样的记录堆在一个框里没有可读性。日志的每日总结必须是人写（或机器起草、人确认）的一句话，提交只能当证据层。这是方案的主要成本，不能绕开。

**二、一天同时跑多条线，不是一条。** 2026-10-15 当天同时有 `wangly-s3-inventory-cleanup`、`wangly-audit-retention`、`sse-sequence-and-factor-contract-audit`、`wenjie-ide-cleanup` 四个计划；2026-10-09 同时有 `grouped-calibration-analysis-speedup`、`general-doris-efficiency` 和一个与实习无关的个人项目计划。所以「一天 = 一条链上的一个节点」的模型是错的，必须允许一天属于多条链。

## 4. 数据模型：证据、记录、链条注册表分三层

三层分开，职责和所有权都不同。这是整个方案最关键的工程决定。

### 4.1 证据层（机器产出，不手改）

`content/journal/_evidence/YYYY-MM-DD.json`，由采集脚本生成，可随时重算。内容是指针，不是叙述：

```json
{
  "date": "2026-10-14",
  "repos": [
    {"repo": "sirui-quant-research",
     "commits": 161,
     "url_template": "https://github.com/MengerWen/sirui-quant-research/commit/{sha}",
     "top_paths": [["因子/algobench", 278], ["reports/2026-10", 102], ["scripts", 61]],
     "items": [{"sha": "...", "subject": "并行执行完整订单验收与日清单编码"}]}
  ],
  "plans": [
    {"file": "PLAN/2026-10-14-szse-model328-four-minute-performance.md",
     "title": "深市 328 列单日四分钟性能验收实施计划"}
  ],
  "outputs": ["reports/2026-10/..."],
  "report": "2026-10-14"
}
```

### 4.2 记录层（人写，受版本管理）

`content/journal/YYYY-MM-DD.md`，和 `content/daily/` 同构，沿用 frontmatter 习惯：

```yaml
---
date: 2026-10-14
headline: "沪市委托 v2 全流程提速，深市 328 列进四分钟档"      # 不超过 40 字，框内那一句
chains: [sse-original-v2, szse-model328]                      # 这天参与的链
highlights:
  - "沪市原始委托 v2 从解析到面板跑通，热副本清理同步做完"
  - "深市 328 列单日基线换成 2025-11-18，240 秒硬门写进计划"
handoff:
  from: [{chain: sse-original-v2, date: 2026-10-13, note: "接住前一天定下的 v2 口径"}]
  to:   [{chain: szse-model328, date: 2026-10-16, note: "四分钟验收转给 16 日续跑"}]
report: 2026-10-14        # 当天有每日汇报时填，构建时校验文件存在
---

（可选正文：当天值得多说两段的事。没有就不写。）
```

`headline` 和 `highlights` 是唯一需要人判断的内容。其余全部可由脚本补齐或校验。

### 4.3 链条注册表（人写，唯一权威）

`content/chains.json`。链条逻辑只在这里声明一次，可 diff、可评审、可回退：

```json
{
  "schemaVersion": 1,
  "tracks": [
    {"id": "infra", "label": "数据与服务器", "stage": "data-processing"},
    {"id": "snapshot", "label": "快照与回放", "stage": "lv2-snapshot"},
    {"id": "footprint", "label": "算法痕迹", "stage": "algo-footprint"},
    {"id": "factor", "label": "因子与定标", "stage": "factor"},
    {"id": "model", "label": "模型", "stage": "model"},
    {"id": "dashboard", "label": "看板与交付", "stage": null}
  ],
  "chains": [
    {"id": "szse-model328", "track": "factor",
     "label": "深市 328 列因子：重算到签收",
     "purpose": "把 328 列因子在 601 个交易日上算完、验收、封存并评价表现",
     "start": "2026-10-12", "end": "2026-10-18", "status": "done",
     "parent": "old-factor-bank",
     "closes_into": {"showcase": "factor", "daily": ["2026-10-16", "2026-10-18"]}}
  ]
}
```

`track` 复用 `config.json` 的六个阶段 id，所以日志和既有两栏共用同一套阶段语言，不新造一套分类，也能从日志跳回对应的正式成果页。`dashboard` 这类工程线不属于任何研究阶段，`stage` 置空。注意轨道**不靠颜色区分**，理由见第 8 节的配色实测。

**为什么不把链条写在每日文件里**：链条是跨天的对象，写在天里就没有单一来源，改一次要改多天，而且无法回答「这条链总共多长、现在什么状态」。注册表 + 每天引用 id，是唯一能既显示日视图又显示链视图的结构。

## 5. 链条怎么判定（难点一）

先说清楚自动化能做到什么程度。我验证过信号强度，结论不乐观但够用。

### 5.1 可用信号，按可靠性排序

| 信号 | 实测强度 | 用途 |
|---|---|---|
| PLAN 文件名的首词族 | 63 个族，17 个跨多天，覆盖 129 个带日期 PLAN 中的 83 个 | 主力聚类：`formal` 11、`szse` 11、`open5m` 10、`sse` 10、`wangly` 6、`ml` 4、`cancel` 3、`grouped` 3 |
| PLAN 文件名的前两词族 | 103 个族，19 个跨多天，覆盖 45 个 | 区分同一大线下的子链，如 `szse-model328` 单独成族（7 个，10-12 → 10-18） |
| `-design` / `-implementation` / `-continuation` 后缀 | 成对出现，如 `ml-no-rf-contract-design` + `ml-no-rf-contract` | 识别「设计 → 实施」这种确定的交接类型 |
| 提交触及路径的重叠 | 可算，未量化 | 给没有 PLAN 的日子找归属 |
| PLAN 正文显式互链 | **只有 1 例**（`2026-10-16-...-continuation` 用 markdown 链接指回 `2026-10-14-...-performance`） | 遇到就当硬边，但不能指望 |

我原本以为 PLAN 正文里「延续」「续跑」「承接」能提供大量显式边——33 个文件命中这些词，但逐个看过，绝大多数是领域术语（「续跑保留检查」指恢复一次中断的计算），不是指向另一个计划。**所以显式链接这条路基本不存在，不要在方案里假设它。**

另有 28 个 PLAN 用中文命名（如「双重价格Gate三参数联合定标与校准提速实施计划」），首词族切不出来，需要一张关键词映射表（定标→factor、Gate→footprint、存储/Doris→infra）兜底。

### 5.2 判定流程：脚本起草，人确认，注册表为准

```
提交 + PLAN 文件 + 路径重叠
        ↓ 脚本聚类（首词族 → 两词族 → 关键词表 → 路径 Jaccard）
     候选链条草案 + 每天的归属建议 + 置信度
        ↓ 人逐条确认或改写
     content/chains.json（权威）
```

脚本只输出草案和置信度，永不直接写 `chains.json`。确认过的链条标 `confirmed`，脚本推断未确认的标 `inferred`。

**置信度要显示出来，不要藏。** 界面上：已确认的交接画实线，推断的画虚线，并在展开层写明依据（「依据：PLAN 文件名同族 + 两天触及 `因子/algobench` 路径重叠 72%」）。这同时解决两件事：不把推断当事实（符合仓库 AGENTS.md 对可追溯的要求），也给图里的两种线宽一个真实理由，而不是为了好看加粗细变化。

### 5.3 交接的四种类型

真实数据里能分出四类，各给一种连接线画法：

| 类型 | 含义 | 真实例子 |
|---|---|---|
| **延续** | 同一目标跨天继续 | `2026-10-14 szse-model328-four-minute-performance` → `2026-10-16 ...-continuation` |
| **派生** | 做一件事时发现的问题分出新链 | `2026-10-16 sse-visible-factor-contract` → `2026-10-16 sse-factor-error-audit` |
| **依赖解除** | 基础设施链让研究链能往下走 | `2026-09-04 wangly-environment-bootstrap` → `2026-09-07 old-factor-bank-implementation-and-300s-gate` |
| **收口** | 链条结束，落成每日汇报或正式成果 | `2026-10-18 szse-model328-factor-performance` → 每日汇报 2026-10-18 → 正式成果「因子构建」 |

这四条可以当实现期的验收用例——图上这四种关系必须一眼能分辨。另外两条真实长链可以当压力测试：

- `2026-10-13 sse-original-order-v2` → `10-14 sse-original-v2-performance` → `10-14 sse-v2-hot-cleanup` → 每日汇报 2026-10-14「沪市委托v2全流程提速」
- `2026-08-16 ml-no-rf-contract-design` → `ml-no-rf-contract` → `2026-08-17 open5m-no-rf-performance-v2-design` → `-v2` → `2026-08-19 open5m-cancel-lag-distribution-design` → 每日汇报 2026-08-19

按首词族和阶段归并，当前可见的线（供确认时参考，不是最终清单）：

- **数据与服务器**：Doris 访问重构与服务器迁移（7 月）→ 内存事故与 RUNBOOK 加固 → wangly 环境与结果转移（9 月）→ wangly 存储盘点、保留优化、S3 清理、产物退役（10 月）→ 存储原则与凭证回填

## 6. 怎么显示（难点二）

> **2026-10-20 定稿**：三个方案都用 91 天真实数据做成了可点开的原型
> （`design-demos/journal-prototype/`）。**最终选定方案 C 的演化版「推进图谱」**，
> 记录在仓库根 `direction-approved.md`。6.1–6.4 保留纸面推演与另外两版的权衡，
> 实际要实现的是 **6.5 定稿**。
>
> 实测改掉的两个原假设：同时在跑的链条最多 **5 条**（月均 2 条），不是本节假设的 8 条；
> 横轴必须用真实日期而不是「有记录的日子等距排列」，否则停摆会被画没。

### 6.1 三个方案

**A. 泳道台历**：纵轴日期，横轴固定 6–8 条轨道，当天在哪条链上活动就在对应格子里放一个框。链条读成列方向的竖带，交接是短的横向连接。

- 好：并行诚实，交接是局部短线，不会连成蛛网。
- 差：一天变成多个框，和「每天一个框」的要求冲突；窄屏放不下 6 列；只跑一条线的日子留大量空格。

**B. 日列 + 链轨（推荐）**：一列，严格一天一个框；框左侧一条窄轨区，每条在跑的链是一条竖线（像 git graph / 地铁图）。当天的框用短刻度接到它触及的那几条线上。链条起点是分叉，交接是并线，结束是收口。

- 好：严格满足「每天一个框」；分叉／并线／收口的语义无歧义，而且是大家已经认识的图形语言；窄轨在手机上也站得住；纵向滚动天然对应时间。
- 差：同时超过 6 条线时轨区会挤；需要一个泳道分配算法（链结束后回收泳道），这是实现成本的主要来源，但 git graph 的做法可以直接照搬。

**C. 链条为主、天为珠**：横轴时间，每条链一条横带，天是带上的点（链条甘特图）。

- 好：链条逻辑和交接最清楚。
- 差：问不出「10 月 14 日我干了什么」，要横跨多条带去找；91 天横向滚动很长；完全不满足「每天一个框」。

### 6.2 推荐：B 做主视图，C 压缩成顶部总览

│    10-11 — 10-12  无记录                                     │  ← 空档压成一条细线，不留空框
└──────────────────────────────────────────────────────────────┘
```

点总览里任一条链，时间轴只高亮这条链上的日子，其余压暗——这就是 C 的筛选能力，不用切模式。

### 6.3 空档、密度与规模

91 天现在，按每月约 20 天增长，一年后约 240 个框。三条处理：

- 月份分组 + 月份标题吸顶，沿用现有 `.timeline-month` 的做法。
- 连续无记录的日子压成一条细线写「10-11 — 10-12 无记录」，不排空框。**停下来的日子也是信息**，但不该占和工作日一样的面积。
- 默认只渲染最近两个月，往上滚动时按月续加（现有站点全量渲染 35 条没问题，240 条起就要分批）。

### 6.4 有每日汇报的日子怎么区分

要求是「不一样的颜色或者形式的标记」。在研究编辑台这套纸墨体系里，换颜色是最弱的做法：纸底本身是暖色，六个阶段色都是低饱和的（实测见第 8 节），再往上叠一个「汇报色」只会多一层互相干扰的弱信号。改用**材质和字体**区分，三档可读的层级：

| 这天的性质 | 处理 |
|---|---|
| 有每日汇报 | 框底换成 `--surface`（比页面底色亮），左侧 3px 墨色实边，标题用衬线显示体，右侧一个「每日汇报 ↗」文字链接 |
| 普通工作日 | 页面底色，一条 `--line-soft` 细线分隔，标题用正文无衬线体 |
| 链条收口（落成正式成果） | 轨区上那一点画成实心墨色方块，框右上角一个到对应阶段的链接 |

三档之间的差别是底色材质、左边界、字体三项同时变化，不是只换一个色值。这样在黑白打印、低对比屏幕和色觉异常下都还读得出来。

### 6.5 定稿：推进图谱

选定方案 C 的演化版。以 `design-demos/journal-prototype/direction-3-atlas.html` 为准，下面是它的规格。

**两个视图，一个数据源**

- **图谱**（默认，宽屏）：一张 SVG。横轴真实日期，纵轴六条轨道，点是当天在某条链上的工作，折线是链条。
- **清单**（窄屏默认，宽屏可切）：一张表，92 行，日期／那句话／链条／提交数／汇报。它同时是图表的无障碍孪生体——图里能读到的，表里都能读到。

**图谱的编码**

| 元素 | 编码 | 理由 |
|---|---|---|
| 横轴 | 真实日期，首日到末日 | 停下来的日子要占真实宽度 |
| 纵轴 | 六条轨道，高度 = 36 + 9 × 该轨道链条数 | 链多的轨道不被挤扁 |
| 轨道内位置 | 每条链一个固定偏移 | 链条身份靠位置，不靠颜色 |
| 点 | 半径 = 2.1 + 0.46 × √提交数，上限 7 | 单日 1–243 次，线性会爆 |
| 点的填充 | 实心 = 当天有每日汇报，空心 = 没有 | 材质区分，不占颜色 |
| 折线 | 相邻活跃日实线，跨空档虚线并降到次要色 | 「这条链停了几天」是信息 |
| 交接弧 | 跨轨曲线，默认 0.26 不透明度；按类型 延续实线／派生 4-3 虚线／依赖解除 1-3 点线 | 默认看链条，追问时才看交接 |
| 收口 | 链条末点上的实心方块 | 与每日汇报／正式成果的连接点 |
| 每日汇报行 | 轨道下方单独一行墨色刻度 | 35 篇什么时候出的，一眼排开 |
| 周末 | 竖向浅底纹，0.3 不透明度 | 节奏信息，但不抢数据 |
| 月分隔 | 实线细线 + 月份标签 | 网格用虚线是噪音 |
| 链名 | 活跃 ≥3 天的链在折线起点直接标注，文字带纸色描边 | 直接标注优于图例 |
| 珊瑚色 | **只**表示当前选中或聚焦 | 全站一处用法，不与「有汇报」抢 |

**交互**

1. 悬停：整列命中（不用对准圆点），灰色竖线对位，浮出小纸卡写日期、星期、那句话、链条、提交数。
2. 点击：选中那天，珊瑚竖线与淡带标记，下方日卡更新；日卡上方有「前一天／后一天」，带相邻日的日期与一句话。
3. 聚焦链条：下拉选、点折线、或点日卡里的链名。其余压到 10%，该链与其上下游亮成珊瑚，日卡换成**链条卡**（上下游、落成了哪几篇汇报、这条链上的每一天）。
4. 时间窗：全部 / 近 3 个月 / 近 1 个月。横轴端点标签与汇报篇数跟随窗口。
5. 键盘：图表可聚焦，←→ 换一天，Esc 取消聚焦。
6. 清单：关键词查找；点一行回到图谱并选中那天。

**为什么要有时间窗**：当前 139 个自然日在 1120px 下每天约 8px，够用；一年之后约 365 天、每天 3px，点会糊成一片。时间窗是这个方向能长期用下去的前提，不是锦上添花。

**仍然成立的约束**：链条不靠颜色区分（见第 8 节实测）；有汇报的日子换材质不换颜色；链条判定脚本起草、人确认，界面区分确认与推断。

## 7. 交互与证据（难点三）

> **2026-10-20 定稿后**：三层的内容不变，承载方式按 6.5 走——第一层是图上的点与悬停读数，
> 第二、三层都在下方的日卡里（不再是列表内就地展开的手风琴）。本节描述的内容分组、
> 折叠规则和证据来源全部沿用。

三层信息，对应要求里的「总结 → 更详细的解说 → 支持总结的根据」。

**第一层：框内，始终可见。** 日期、星期、一句话标题（不超过 40 字）、这天的链条名、标记（汇报／收口）。密度目标是一屏能扫完一周。

**第二层：悬停或聚焦。** 框轻微抬起；轨区里这天触及的链条线加亮，其余压到 30% 不透明度——这是整个页面唯一一处主动动效，也是它存在的理由：把「这天属于哪条线」一次说清。同时把 `highlights` 的 2–3 条要点显示出来。

**第三层：点击就地展开**（手风琴，不是弹窗——弹窗会丢失上下文位置，而这个栏目的价值就在上下文）：

几条约束：

- 提交默认折起，只显示数量和触及路径分布，展开才列条目。一天 161 条提交，默认全列会把页面撑垮。
- 提交 hash 以文字显示并带 GitHub 链接。链接可能对方没权限打开，所以 subject 和路径统计必须在本地就有意义，不能让证据的可读性依赖外链。
- 深链：`#/journal/2026-10-14` 打开并展开那天；`#/journal?chain=szse-model328` 打开并筛选到那条链。和现有标签分享链接的习惯一致。
- 键盘：框是 `button`，Enter/Space 展开，上下键移动，焦点可见。
- 链条归属在框里有文字标签，不只靠轨区的线——轨区是冗余强化，不是唯一载体，否则色盲和读屏用户拿不到这个信息。

## 8. 视觉

沿用已批准的方向 B「研究编辑台」（`direction-approved.md`，2026-08-11）。不重新探索视觉方向，理由和 2026-09-18 模型报告、2026-10-18 成果报告一致：同一站点第三个主视图另起一套视觉会破坏整体可信度。按 huashu-design 的规定，这属于「同一项目内已选定方向后的迭代」，不走三方向门；本记录即为依据。

### 8.1 链条线不上色（有实测依据）

我原本打算把六个阶段色 `--stage-0` … `--stage-5` 直接用在轨区的链条线上。按 dataviz 的分类色六项检查跑了一遍（纸底 `#f2eee4`、light 模式、相邻对），结果是不合格：

```
[FAIL] 饱和度下限   4/6 在下限之下，2px 线上会读成灰：
                    #7c8581 (C 0.012)、#4d7c8b (0.056)、#477d75 (0.059)、#9a705d (0.061)
[FAIL] 色觉异常分离 最差相邻对 #9a705d ↔ #d9654f  ΔE 3.0（红色盲）
[FAIL] 正常视力下限 最差相邻对 #477d75 ↔ #4d7c8b  ΔE 3.7（门槛 15）
[WARN] 与底色对比    #aa8439 仅 2.99:1
```

这套色是为正式成果页的阶段步进器和标签做的——大色块、大字号，在那里没问题；缩成 2px 的线、六条并排，就不成立了。两条路：重新推一套能过检查的六色（会引入更饱和的色，和这套克制的纸墨体系打架），或者**不用颜色承担身份**。

选后者：

- **轨区全部用墨色 `--text`**，线宽 2px。链条的身份靠两件事承担：**泳道位置**（同一条链永远在同一列，结束才回收）和**框内的文字标签**（链条名）。
- 颜色只表示**状态**，不表示身份：当前筛选或悬停的链用 `--focus`（珊瑚），其余压到 30% 不透明度。全站同一处用法，和「当前焦点」在别处的含义一致。
- 轨道（六条大线）之间靠**泳道分组间隙**和顶部总览里的轨道名区分，不靠色相。
- 阶段色留在它本来有效的地方：正式成果页的阶段导航，以及日志里跳回阶段的那个链接。

附带好处：一条墨线的地铁图比六条低饱和彩线更像这个站点该有的样子，而且少了一整块无障碍债。

### 8.2 其余落法

- 颜色全部取自 `tokens.css`，不新增变量。
- 字体沿用：标题 `--font-serif`（Libre Baskerville + Noto Serif SC），正文 `--font-body`，不引入第三种字体。
- 轨区线宽 2px，交接处用 6px 圆角折线而不是贝塞尔曲线——直角折线和这套「锐利分隔线 + 2px 圆角」的出版物语言一致，曲线会显得像流程图工具。
- 动效只有三处：链条高亮（120ms，`cubic-bezier(0.23, 1, 0.32, 1)`）、展开（220ms 高度 + 透明度，同一曲线）、框按下 `scale(0.995)`。不做逐框滚动入场——几百个框各自淡入是明确的套路化处理，而且会卡。`prefers-reduced-motion` 下保留透明度变化，去掉位移。
- 手机：轨区压到 16px 宽，只画当前筛选的链；总览横向滚动；框内不显示提交统计。

**一处技能冲突需要说明**：design-taste-frontend 的 house rules 禁止细分隔线、禁止 `01/02/03` 编号、禁止中点连接的元信息串、禁止小号全大写标签——而本站已批准的研究编辑台方向恰恰刻意使用了这几样（`INDEX / 01—06`、`Research edition no. 06`、hairline 分隔）。按该技能自己的规定（brief 的原话总是优先）和 impeccable 的同类条款，以本项目已批准的方向为准，新栏目延用这套语言。代价是新栏目在通用「反套路」尺度上不会得分高；收益是和既有两栏同属一个出版物，这对一个档案站更重要。

## 9. 构建与发布

### 9.1 一条硬约束

**Cloudflare Workers Builds 只 clone `internship-dashboard` 一个仓库**（`DEPLOY.md` 第 1 节第 4 条）。研究主仓和父仓在构建环境里不存在。所以：

- 采集脚本**只在本地跑**，产物（`_evidence/*.json`）**提交进 dashboard 仓库**。
- `build.py` 只读已提交的 JSON，绝不在构建时调别的仓库的 git。
- 这和现有 `published_at` 取 git 时间遇到浅克隆时降级到 mtime 是同一类问题；那里选了降级，这里不能降级（证据不能「大约」），所以必须预生成。

### 9.2 新增文件

```
content/chains.json                        链条注册表（人写）
content/journal/YYYY-MM-DD.md              每日记录（人写）
content/journal/_evidence/YYYY-MM-DD.json  证据（脚本生成）

### 9.3 范围与隐私

采集要排除：

- 与实习无关的内容：`dating-*`（6 个 PLAN）、`记账` 仓库、`wenjie-ide-cleanup` 这类本机环境整理。排除规则在 `journal_repos.json` 里显式列出，不靠猜。
- 本机绝对路径。PLAN 正文里有 `C:/Users/19927/Documents/...` 这类路径，不能发布到站点。
- 服务器主机名、账号、内部地址。站点虽在 Cloudflare Access 后面，但正式成果和每日汇报是会拿去汇报和面试的，日志作为第三栏同样会被看到。

### 9.4 搜索

`dist/journal/*.html` 的展开层内容纳入 Pagefind 索引，这样全文搜索能搜到「哪天动过 wangly 存储」。成本很低，默认打开。

## 11. 风险与取舍

1. **粒度落差是主要成本。** 2715 次提交不能自动变成 92 句话。不接受「人写一句话」这个成本，这个栏目就会退化成提交流，没人会看第二次。
2. **链条判定是启发式的。** 首词族覆盖 83/129，显式互链只有 1 例。方案的处理是：脚本起草、人确认、界面区分实线虚线并写明依据。不要在没确认的边上用实线。
3. **跨仓库耦合必须在本地断开。** 见 9.1。如果哪天把采集放进构建，Cloudflare 上会静默产出空证据。
4. **并发链条数会涨。** 当前 6 条，上限定 8 条。超了就要在注册表里合并链条，或者接受轨区在宽屏之外退化成「只画筛选中的链」。
5. **和每日汇报可能重复。** 防线是硬性字数限制：`headline` 不超过 40 字，`highlights` 不超过 3 条。有长内容就写成每日汇报，日志里只放链接。
6. **视觉上放弃了一部分「反套路」得分**，换与既有两栏的一致性。见第 8 节末。
7. **轨区不上色之后，链条数多了会更依赖泳道位置。** 泳道一旦错位（算法回收泳道时把两条链排到同一列的相邻段），读者会把两条链看成一条。实现期要对泳道分配单独写测试：同一条链在其存续期内列号不变，回收的列号与前一条链之间至少隔一天。
