# 研究日志每日更新规则

自 2026 年 10 月 21 日起执行。每天北京时间（Asia/Shanghai）上午 9 点，在本聊天回顾前一自然日的研究工作，将有证据的新进展归入研究日志。更新对象是本仓库的 `content/journal/` 与 `content/chains.json`；线上入口为[研究日志](https://internship-dashboard.mengerwenjie.workers.dev/#/journal)。

## 日期与补漏

- 目标日为运行日的前一天，范围为北京时间 00:00 至次日 00:00，左闭右开。9 点是整理时间，工作归属使用实际发生日期。
- 对 Git 时间统一换算到北京时间，保留 author time 与 committer time 的区别。跨日提交、补写报告和延迟推送，结合原始记录确定工作日；提交日、推送日、汇报名义日和发布日分别记录。
- 首次定时运行从 2026-10-20 开始核对，补上现有固定快照之后的工作。之后按每日核对记录补齐漏跑日，并复查近 7 天的迟到提交、文档和未解决缺口。更早的新证据仍补回实际工作日，注明补记日期。
- 某日已有日志不代表覆盖完整；按来源和证据核对。重复运行只补新增事实，已覆盖的成果不重复写。
- 完成来源检查后确无新增工作，保留空白日期，不为每一天生成占位日卡。来源无法读取时记为覆盖不完整，留待补核。

| `Quant_Research-Trading` | 仅配置中的思瑞投资白名单目录；研究计划、文档及仓库指针变更。排除其他项目和私人内容。 |

| 本地未提交材料 | 范围内的已修改文件和相关新文件，包含旧 PLAN 的新进展。结合差异、原始内容和会话记录判断，不仅凭文件名或 mtime 认定当天完成。 |

先记录各仓库本地 HEAD、远端查询时间及远端分支 SHA。使用只读查询或 fetch 获取远端证据，不切换、拉取覆盖或提交源研究仓库。记录采集期间的版本变化；新增提交留到后续补核，不能把不同时间的状态混成一次完整快照。

完整枚举目标时间范围内的提交和变更文件；围绕各项实质工作阅读对应 diff、计划及结果。`_evidence` 中每仓的前 10 条提交仅作展示线索。父仓子模块指针与子仓实际成果按同一 SHA 关联，避免重复计为两项成果。

本地草稿标明未提交，计划标明计划。会话中的原始用户要求和决定可直接佐证当时的目标、约束、取舍、停止或转向；助手汇报、用户粘贴的结果和压缩摘要分别标明身份。完成、性能、推送、服务器同步、运行和验收结论仍须回查对应的原始工具回执、结果文件及当前状态，不能只凭一句“已完成”。记忆只用于定位。服务器证据不足时保留已确认的状态及缺口，不为写日志启动计算、部署或中断任务。

## 会话核对与入库

1. 用 `scripts/journal_sessions.json` 核对本机来源、项目目录与历史路径；读取失败、目录缺失、记录截断分别报告，不将空列表解释为当天没有工作。候选范围可能包含同项目目录下的无关聊天，逐条选择与本次研究目标有关的消息。
2. 按消息自身的带时区时间换算到北京时间，显式指定 `--since` 与 `--until`。会话创建日、归档日和文件 mtime 不作为工作日。复制的前文、fork 继承内容、补写总结和多份物理副本去重；消息保存时间不能独自证明被转述事件发生的日期，原有日期待核项需另有证据才能关闭。
3. 运行 `python scripts/collect_journal_sessions.py --since YYYY-MM-DD --until YYYY-MM-DD --output data/journal-sessions/YYYY-MM-DD.json`，全文候选索引只存本机 `data/`。该脚本不调用模型、不执行历史指令、不续跑历史代理、不改会话文件；工具回执需要时按原始行另读，不能把用户贴出的代码或日志当作本次实际执行。
4. 将已核对且适合本站读者的必要片段保存到本次 `docs/journal-review/.../reviewed-excerpts.json`，沿用[首份清单](session-evidence-2026-10-21/reviewed-excerpts.json)字段。说明每条支持什么，关联实际存在的（日、链条）。全文、凭据、邮箱、地址与私人内容不入站；剪裁后仍须保留否定、条件、角色和上下文，不能用删词改变原意。
5. 运行 `python scripts/collect_journal_sessions.py --output data/journal-sessions/YYYY-MM-DD.json --verify 审阅清单路径 --render`。命令逐字核对摘录和真实原始行哈希，通过后只更新清单涉及日卡的“会话佐证”区；加 `--check` 只比较、不写入。独立的 Git 证据采集器继续管理 `_evidence/`，不会覆盖会话正文。保存审阅清单、覆盖日期与读取缺口，不能把候选条数称为已确认成果数。
6. 摘录沿用现有正文展示，保留此前的 headline、人工内容、链条和交接。会话若揭示漏记工作、错误日期或方向变化，再结合原始材料按下面的归并规则修改；没有直接支持既有日卡的消息时保留缺口，不凑摘录。

## 按成果整理与归并链条

先列出当天各项工作的目标、实际动作、新结果、证据、当前状态及承接关系，再与现有链条的 `purpose` 和历史记录对照。

- 同一研究问题下的实现、排障、提速、补验、修正和交付，归入原有链条。并行工作分别保留，每个（日、链条）写一条具体注解。
- 新工作有独立目标，且不能合理归入现有链条时，自行创建稳定 id、明确名称与 purpose，优先使用已有 track，记录新建理由。证据只能支持暂定归属时，保留待核状态。
- 只有输入、结果、方法或明确决策存在承接时才登记 handoff；同日发生、先后出现或名称相似不构成承接。
- 正常增量维护保留既有链条 id、历史日期和人工内容。确需合并重复链条时，说明依据，迁移所有引用与交接，保留原 id 的去向；有歧义则保留原结构并记录缺口。
- 有新证据才调整链条状态或去留。代码提交、运行结束、验收通过和正式交付分别判断；一次回滚不直接认定整条研究方向被放弃。局部未采用的尝试写在对应日点上。

无需为普通归类、新链建立和增量补记逐项等待确认；研究方向、实验执行和其他项目的操作仍按原授权办理。

## 写入方式

沿用现有数据格式，不改页面布局或交互。每日记录包含：

1. 一句具体的 `headline`，概括当天的主要进展，避免把提交标题直接拼起来。
2. 每条链的短 `note`，说明这一天在该链上做了什么。
3. `highlights` 说明结果、关键决策和仍未解决的问题；有必要时在正文补充原因、试验比较、失败及下一步。
4. 能支持结论的提交链接、仓库相对文档路径或结果收据；`reports_covering` 只关联确实覆盖该项工作的真实汇报。

链和关系沿用2026-10-21审计后的证据字段。链及handoff的`source_refs`保存仓库、完整revision、文件路径/行号或commit及固定GitHub链接。每条关系写明承接对象、方法/输入类型和版本边界，并登记`source_date`与`date`；两日必须分别存在于来源链和目标链的日点中。来源日表示被连接的阶段记录，承接日表示后项记录。

每条链保留`report_coverage: curated`，只把确实覆盖本链的汇报加入`closes_into.daily`；没有对应汇报时用空列表。日卡的`reports_covering`是当天相关报告的集合，不能直接复制为每条并行链的成果。日期无法闭合时，在`date_notes`记录具体链、日期线索及缺口，同步`review.unreviewed_days`，并在正文解释名义日、入库日与实际工作日。

合并同一成果的多次修补提交，保留不同工作的有效信息。写“已完成”须满足对应完成条件；测试数量、性能数值和效果改善须有原始结果。更新原日卡时保留人工文字，只修改有新证据或需要纠正的部分。涉及旧日结论的修正注明原因和补记日期。

按已安装的 `shuorenhua` skill 写作。入站正文及证据继续隐去凭据、邮箱、内网地址和服务器绝对路径；可引用仓库相对路径及适合本站读者的 GitHub 链接。

## 保存、检查与发布

任务点大小单独读取`content/journal/_attribution/`的逐条归属清单。更新固定证据后，运行`python scripts/collect_journal_attribution.py`并复核本轮新增/变化的归类，再运行同命令的`--check`。规则中的`reviewed_through`限制已审阅日期，超出日期的提交先标待核；完成本轮逐条核对后再更新该日期。新增研究目标、公共代码或新阶段不能仅靠旧关键词自动确认；在`scripts/journal_attribution_rules.json`补明确规则或逐SHA处置，证据不足保留`pending`。跨链提交只有确实交付多个独立目标才等分；共用模块、下游消费或旧研究名称不构成多次计重的依据。构建会核对每仓总数、提交唯一性和份额守恒；缺归属时保留最小定位点，不得回退到当天总量。相关检查增加`tests/test_journal_attribution.py`。链的工作日期和Git入库日期仍分别解释；归属清单中“当日未设图点”的记录供后续补核，不自动覆盖人工日卡。

1. 在 `docs/journal-review/daily-updates/YYYY-MM-DD.md` 保存本次核对记录，日期为运行日。同日重跑更新原记录。记录覆盖日期、逐来源版本与读取结果、归链决定、修改文件、验证结果、缺口，以及提交、推送和线上核验的独立状态。该目录首份记录产生前，首次待核日期为 2026-10-20。
2. 沿用采集器时显式固定各仓库 revision，并按需要使用 `--since` 缩小范围。现有采集器按 author date 分日、按计划文件名归档且只展示前 10 条提交；以完整枚举和原始材料补核实际工作日。它也没有截止日期，会处理 `--since` 之后所有日期，且可能删除预期集合之外的证据文件。先备份或用临时配置核对 diff，只保留本次已审阅的变更，保留既有人工补充与无关日期。历史快照的版本说明保持真实。
3. 核对 frontmatter、链条 id、逐点注解、报告引用与证据链接，确认新链和 handoff 可被当前格式读取。内容变更运行 `D:\MG\anaconda3\python.exe -m pytest tests/test_journal_build.py tests/test_journal_evidence.py tests/test_journal_provenance.py -q` 和 `D:\MG\anaconda3\python.exe build.py`；取数或连线代码改动同时运行`npm test`。`collect_journal_evidence.py --check`仅证明指定配置与采集产物一致，不能代替来源完整性审阅。`verify_journal_sources.py`核验本次审计目录中的固定引用；以后新增引用仍须回查其实际Git对象和行号。
4. 研究日志实际变化后，按 `AGENTS.md` 用浏览器检查受影响日期、链条、日卡和证据；涉及新链时检查其引用和交接。线上受登录或其他条件阻塞时，分别报告本地结果和线上未验证范围。
5. 只定向暂存本项文件，在本仓库 `main` 提交最小完整改动集合并推送。保留其他任务的修改，核对待推送历史；有不属于本任务的待推送提交时不夹带。远端确认目标 SHA 后记录推送成功。本站 push 会触发既有自动构建，查询发布收据并核对线上内容后才称已发布；发布失败保留本地成果和失败证据。
6. 无内容变化但完成了来源核对时，可仅保存核对记录，避免用更新日志自身制造新的研究成果。推送、发布和资料缺口保留为后续待核项；同一问题持续存在时不重复制造日卡或通知。

这项任务仅维护研究日志及相关证据、规则和核对记录，不替源研究仓库提交或同步服务器，不启动训练、回测、全历史计算，也不代发消息。
